# 433 MHz radio stack: Home Assistant quality comparison

**Research cutoff:** 2026-11-15

**Audited PiPhi revision:** [`8c69c0d`](https://github.com/PiPhi-io/piphi-apps/tree/8c69c0d1715c2bdecdb2d5125e4eef2395cf4652)
**Scope:** `piphi-network-433mhz` 0.1.7 and its required `piphi.service.rtl433-bridge` 0.1.6, assessed as one receive-only radio stack.

## Executive conclusion

The stack is a useful **early receive-only adapter**, not yet a dependable general-purpose sub-GHz product. Its strongest property is architectural restraint: upstream `rtl_433` does the RF decoding, PiPhi executes it without a shell, and PiPhi exposes no transmit action. Unit/contract tests cover the principal happy paths, process restart, packet forwarding, discovery, configuration rehydration, metric extraction, authenticated delivery to Core, and leak transitions.

The stack must not, however, claim the breadth of `rtl_433` as PiPhi device support. At the cutoff, upstream assigns decoder IDs through 398 (with gaps and some decoders disabled by default), spanning weather sensors, utility meters, TPMS, security devices, remotes, LoRaWAN and more; it also warns that RF-derived output is untrusted and can overload downstream recipients ([upstream README and decoder list](https://github.com/merbanan/rtl_433/blob/f15b67699e902522014e7593d060ad37410eda00/README.md#supported-device-protocols), [security warning](https://github.com/merbanan/rtl_433/blob/f15b67699e902522014e7593d060ad37410eda00/README.md#security)). PiPhi has product semantics for only a small field-oriented slice: basic weather, contact, leak, battery and signal values. It has no model qualification matrix, model-specific normalization, decoder safety policy, staleness/availability, packet deduplication, bounded ingress, RF health state, real-hardware evidence, or end-to-end MQTT security story.

Compared with the first-party Home Assistant **MQTT** behavior plus upstream's owning `rtl_433_mqtt_hass.py` adapter, PiPhi is easier to understand but materially less mature in entity metadata and lifecycle. Home Assistant itself does **not** ship a first-party `rtl_433` Core integration or official `rtl_433` app at this cutoff; the fair baseline is therefore HA's first-party MQTT discovery contract and the upstream-owned HA discovery example, not a nonexistent HA decoder integration. HA MQTT supports stable unique IDs/device identifiers, grouped device discovery, device classes, state classes, diagnostic categories, availability and expiry semantics, retained or birth-triggered rediscovery, TLS/client certificates, and discovery removal/update behavior ([HA MQTT documentation](https://github.com/home-assistant/home-assistant.io/blob/c61ecf719cbe63ab1df41d57015e47f91394ad3a/source/_integrations/mqtt.markdown#mqtt-discovery)). The upstream adapter maps a much larger but still explicit set of fields, can restrict IDs, sets HA metadata, supports TLS credentials, optionally sets `expire_after`, and deliberately skips unknown fields ([upstream HA adapter](https://github.com/merbanan/rtl_433/blob/f9a2b3c8a81a54d944216950f0a70611d7a1c0bb/examples/rtl_433_mqtt_hass.py#L93-L625), [publication and identity logic](https://github.com/merbanan/rtl_433/blob/f9a2b3c8a81a54d944216950f0a70611d7a1c0bb/examples/rtl_433_mqtt_hass.py#L671-L806)). That adapter is explicitly an upstream example, not a Home Assistant guarantee, and it also warns about retained false positives and lingering entities.

**Release recommendation:** keep the stack **experimental/unrated** and advertise only the honest supported slice below. Do not describe it as generic support for all `rtl_433` devices, and do not treat leak/contact output as safety or security qualified until P0 controls and hardware qualification exist.

## Honest supported slice

What can be defended from source and tests today:

- Linux container deployment with one locally attached RTL-SDR-style USB receiver, one selected frequency, auto gain or a user-supplied gain, and optional numeric decoder selections.
- Passive JSON reception through `rtl_433 -F json`; default command construction supports 315, 433.92, 868 and 915 MHz presets and custom frequencies ([bridge command builder](https://github.com/PiPhi-io/piphi-apps/blob/8c69c0d1715c2bdecdb2d5125e4eef2395cf4652/apps/services/piphi-rtl433-bridge/src/piphi_rtl433_bridge/config.py#L251-L271)). This does not imply that one frequency/sample-rate/default decoder set can receive every protocol in those bands.
- Forwarding over local HTTP by default, with optional MQTT publication. Username/password and QoS are supported; MQTT TLS is not exposed.
- Manual acceptance of discovered devices keyed by `model + station/device ID + channel/subtype`.
- Basic weather values: Celsius/Fahrenheit temperature, humidity, one average wind-speed family, cumulative rain, pressure, numeric battery voltage, and numeric fields that pass generic filtering. Stable units are only assigned to a subset.
- Contact state only when a decoder emits `contact_open` or `state=open|closed`.
- Leak state only when a decoder emits one of `leak`, `water`, or `moisture`; transition events require a prior Boolean state and are not certified alarms.
- `battery_ok` passthrough and one signal metric. This is not a normalized battery percentage. `snr` is currently collapsed into `signal_rssi`, which is semantically and dimensionally unsafe.
- Receive-only operation. There is no supported transmit, replay, pairing, arming, lock, siren, actuator, remote-control, or RF command path.

Everything else decoded by upstream is, at most, **opaque packet transport awaiting PiPhi qualification**. In particular, utility consumption, energy, air quality, lightning, soil, tank, TPMS, smoke/heat, security, button/remote and actuator-like protocols are not product-supported merely because `rtl_433` can decode some of them.

## Analogical Home Assistant IQS assessment

This is **not an official Home Assistant IQS score**. IQS grades integrations included in Home Assistant Core against HA-specific rules; PiPhi has a different runtime and there is no HA `rtl_433` Core integration to score. The analogy below applies the tier outcomes—UI setup, reliability, documentation, diagnostics, test depth and efficiency—not HA file-layout rules. HA defines Bronze as the minimum reliable/UI/documented/tested baseline, Silver as robust offline/auth recovery with maintainership and troubleshooting, Gold as comprehensive UX/discovery/reconfiguration/diagnostics/full coverage, and Platinum as technical and efficiency excellence ([official IQS definitions](https://github.com/home-assistant/developers.home-assistant/blob/8190fb98f71d250a07b24f962b7019676a15fb5c/docs/core/integration-quality-scale/index.md#scaled-tiers)).

| Analogical tier | Result | Rationale |
|---|---|---|
| Bronze | **Partial; not achieved as a radio stack** | UI schemas, manifests, end-user READMEs and meaningful setup/runtime tests exist. But the advertised generic scope is not bounded by a supported-device list, the production image is not built in PR CI, privileged execution is excessive, and no real receiver/device proves the basic setup path. |
| Silver | **Not achieved** | Process restart and MQTT subscriber retry exist, but offline/RF loss never marks entities unavailable; HTTP/MQTT authentication failure is not classified; fixed retries can flood/stall; no USB/broker recovery qualification or practical troubleshooting/repair state exists. |
| Gold | **Not achieved** | Passive discovery and UI reconfiguration exist, but identity, entity semantics, staleness, diagnostics/redaction, translations, compatibility documentation, hardware qualification and near-complete behavioral coverage are absent. |
| Platinum | **Not achieved** | The receive loop has head-of-line blocking, unbounded retry, duplicate delivery and per-packet synchronous persistence/event amplification. Privileged host access and unpinned upstream decoding also preclude technical-excellence claims. |

**Overall analogical rating: below Bronze / experimental.** That rating is about the integrated product contract, not the quality or decoder breadth of upstream `rtl_433`.

## Safety invariants

These are release gates, not aspirations:

1. **Receive only:** no PiPhi action, profile, raw-command option or behavior may transmit, replay, jam, arm/disarm, unlock, actuate, or claim control of an RF device. Any future TX work is a separate threat model, hardware path and product.
2. **RF is hostile input:** no packet causes command execution, configuration mutation, privilege change or unbounded allocation. Validate type, range, length and model-specific meaning before telemetry/event publication.
3. **No safety claim from generic fields:** leak, smoke, heat, contact, alarm and tamper semantics require an allowlisted decoder/model, captured fixtures, real-hardware transition tests, false-positive review and documented loss behavior. Unknown or ambiguous fields remain diagnostic/unsupported.
4. **Stable identity or no device:** never configure a device whose decoder/model lacks a proven stable identifier. Identity includes every required discriminator and has explicit migrations; `unknown` is not a device identifier.
5. **At-most-one product transition per RF observation:** duplicate RF repeats, transport retries and simultaneous HTTP/MQTT paths must not duplicate state transitions or safety events. Delivery semantics and fingerprint windows are explicit and tested.
6. **Stale means unavailable:** each qualified model has a justified expected cadence and expiry policy. Loss of receiver, decoder process, forwarding path or device packets cannot leave a stale value looking current.
7. **Units are exact:** preserve source meaning; never label SNR as RSSI/dBm, counters as instantaneous measurements, or raw battery flags as percentages. Unknown dimensions have no fabricated unit/state class.
8. **Bounded under RF flood/outage:** queues, packet sizes, cardinality, cache writes, logs, telemetry and discovery events have measured limits and observable drop/coalescing policies. A destination outage cannot stop draining the decoder indefinitely.
9. **Least privilege:** production cannot expose arbitrary executable overrides. The service runs non-root with only the selected receiver device and minimum filesystem/network access; administrative reconfiguration is authenticated and audited.
10. **Secrets and household RF data stay private:** TLS is verified when crossing the local trust boundary; credentials never enter diagnostics/logs; identifiers, packet contents and occupancy-like history are access-controlled, redacted and retained only as documented.
11. **Upstream is pinned and qualified:** image digest, `rtl_433` version, enabled decoder set and field schema are traceable to the PiPhi release. Decoder updates repeat regression and hardware qualification.
12. **No support by implication:** documentation and UI distinguish “decoded by installed `rtl_433`” from “supported and qualified by PiPhi.”

## Prioritized work

### P0 — before a reliable or safety-capable release

1. **Close the execution/privilege boundary.** Remove `rtl433_command` from production configuration; validate frequency/device/gain/protocol IDs; authenticate `/radio/config` and `/ingest/rtl433`; run non-root/unprivileged with one explicit receiver mapping and a read-only filesystem.
2. **Pin the actual RF stack.** Pin `rtl_433` to a reviewed version/package digest, record its enabled decoder set, align Docker Hub/GHCR references, make 0.1.7 depend on the actually qualified bridge version, and build/smoke-test both containers on every PR.
3. **Implement bounded, idempotent ingress.** Add packet size/type/range limits, a bounded queue, retry budget with exponential backoff/jitter and circuit breaking, separate destination acknowledgements, cross-transport/RF-repeat fingerprints, metrics for queue depth/drop/retry/duplicate counts, and no synchronous cache rewrite per packet.
4. **Implement receiver/device availability.** Health must reflect decoder task/process, SDR open/read status, last successful forward and destination status. Define per-qualified-model expiry; mark state unavailable on USB loss, process death, stale packets or forwarding failure, and recover without stale-to-current ambiguity.
5. **Fix semantic correctness.** Keep RSSI, SNR and noise separate with correct units; normalize only documented fields; remove permissive unknown-scalar entity creation from the supported path; validate battery/contact/leak values and weather ranges; define cumulative counter behavior.
6. **Constrain safety events.** Disable canonical leak/security mapping for generic profiles until model/decoder allowlists, first-observation policy, stale policy, duplicate policy and hardware evidence exist. Never infer certified safety from the presence of a key alone.

### P1 — before broad beta

1. Publish a machine-readable support matrix: exact decoder ID, model string, frequency/modulation/sample-rate needs, identity fields, entities, units, cadence/expiry, known collisions, fixtures, hardware/firmware and qualification status.
2. Build model-specific adapters for a deliberately small initial cohort (for example, two weather families, one contact and one leak family). Keep all other packets in a rate-limited diagnostic discovery lane.
3. Add MQTT TLS/CA/client-certificate support, broker availability/LWT behavior, unique client IDs per receiver, credential failure reporting and reconnection tests. Define whether HTTP **or** MQTT is authoritative; do not silently enable both into one consumer.
4. Version identity and migration. Include protocol/model/type/subtype/channel only where required by that decoder, reject missing stable IDs, handle sensor ID rollover explicitly, and test upgrades without duplicate devices.
5. Add privacy-safe downloadable diagnostics: pinned versions, sanitized command, receiver selector hash, process state/exit reason, last-packet ages by configured device, queue/drop/retry counters and redacted decoder stderr. Exclude raw payloads, credentials and full RF IDs by default.
6. Add replay/integration tests using reviewed `.cu8`/pulse fixtures, a real MQTT broker with auth/TLS, HTTP+MQTT duplicate/failure orderings, malformed/oversized packets, noisy unknown devices, event-rate limits, process/USB/broker loss and restart.
7. Clarify user documentation: antenna/band/regulatory caveats, kernel-driver conflict, gain and receiver selection, unsupported disabled decoders, troubleshooting, privacy, no-transmit guarantee and support-vs-decode distinction.

### P2 — maturity and scale

1. Establish a real-hardware rack across amd64/arm64 with serial-pinned receivers and representative supported devices; test cold boot, hot unplug/replug, RF shielding/loss, weak signal, collisions, battery-low, ID rollover, multiple receivers, 24–72 hour soak and upgrade/rollback. Publish immutable qualification evidence per release.
2. Add adaptive telemetry coalescing while preserving meaningful transitions; batch cache persistence; expose event-volume budgets and benchmark sustained hostile/noisy RF conditions.
3. Support multiple receivers/frequencies as explicit source devices with topology, independent health and collision-safe identity rather than one mutable global process.
4. Add localized UI/help, repair flows, compatibility warnings for decoder changes, support-bundle tooling, and measured coverage/typing/security scans appropriate to a Gold-like product claim.
5. Evaluate direct upstream MQTT output only after threat-modeling it. It offers availability/TLS/topic features, but replacing the bridge is beneficial only if PiPhi retains validation, deduplication, bounded flow and model qualification.

## Validation and environmental limits

- `piphi-network-433mhz`: **36 tests passed** in 1.61 s using an isolated Python 3.12 virtual environment and `pip install -e '.[dev]'`.
- `piphi-rtl433-bridge`: **53 tests passed** in 0.19 s using an isolated Python 3.12 virtual environment; its PDM dev group is not a PEP 621 `dev` extra, so `pytest>=9.0.3` was installed explicitly after the editable package.
- The initial repository-local `pdm run pytest` attempts were not valid test results: PDM selected its Python 3.13 environment despite the packages requiring 3.12, then pytest collection was blocked by a missing harness-global `piphi_runtime_testkit_python` plugin. The isolated 3.12 runs above resolved that environment issue without repository changes.
- No RTL-SDR, antenna, RF fixture, MQTT broker, PiPhi Core deployment, container runtime, USB hotplug facility or real sensor was available. Therefore RF sensitivity, decoder correctness, device compatibility, process/USB recovery, broker/TLS behavior, privilege reduction, multi-arch images, throughput and real-hardware claims remain **unverified**.
- No coverage report was generated, and passing unit/contract tests must not be read as hardware qualification.
