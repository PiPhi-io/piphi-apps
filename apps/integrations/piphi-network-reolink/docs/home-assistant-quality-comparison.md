## Executive conclusion

The package is an honest **early read-only connection/inventory prototype**, but it is not yet an honest general “Reolink cameras” integration and does **not** meet the current Home Assistant Bronze baseline. The marketplace `beta`, `1%` rollout, and `qualification.status: unverified` flags are appropriately conservative; `quality_tier: bronze` is not supported by the evidence.

The implemented slice is:

- manual configuration of one local host address plus credentials;
- lazy authentication through `reolink-aio`;
- periodic host refresh;
- aggregate `connected` and channel-count state;
- a host entity and informational channel child records containing name, model, firmware, online flag, doorbell flag, and a filtered feature list;
- one read-only `refresh` action; and
- process-memory secret handling that excludes the password from normal state/events/diagnostics.

It does **not** provide camera media, snapshots, recordings, detection events, doorbell events, push subscriptions, per-channel state publication, camera controls, firmware management, automatic discovery, tested setup, reauthentication, safe reconfiguration, stable hardware identity, or hardware-backed compatibility evidence. Home Assistant’s first-party integration provides all major camera surfaces and is declared Platinum, local-push, and pinned to `reolink-aio==0.23.1` in the cutoff manifest ([manifest](https://github.com/home-assistant/core/blob/12e4d38035bce70d6b20167da23f37a31d1416bf/homeassistant/components/reolink/manifest.json)); its own rule ledger marks every Bronze-through-Platinum rule done or exempt ([quality ledger](https://github.com/home-assistant/core/blob/12e4d38035bce70d6b20167da23f37a31d1416bf/homeassistant/components/reolink/quality_scale.yaml)).

### Explicit Bronze verdict

**Verdict: FAIL — do not publish or retain a Bronze label.** Under a PiPhi-adapted reading of Home Assistant’s 20 Bronze rules, 6 are satisfied, 1 is reasonably exempt, and 13 are unsatisfied. A tier requires every rule in that tier; partial implementation is not sufficient. The authoritative cutoff rule list is in Home Assistant’s hassfest source ([`ALL_RULES`](https://github.com/home-assistant/core/blob/12e4d38035bce70d6b20167da23f37a31d1416bf/script/hassfest/quality_scale.py#L29-L52)). “Beta/1%” limits exposure but does not compensate for failed quality gates.

Until P0 is complete, label the package **experimental/unqualified** and describe it as a **local Reolink host connectivity and channel-inventory monitor**.

## Safety and privacy invariants

These are release-blocking invariants, including for future capabilities:

1. **Never publish or log secrets:** passwords, session tokens, authorization headers, camera UID where treated as secret, Wi-Fi details, raw API responses, or URLs containing credentials. Redaction must cover encoded and decoded forms and exception strings.
2. **Never expose an upstream media URL:** streams and snapshots must be fetched through a bounded authenticated broker; use short-lived opaque handles, enforce config/channel authorization, prevent SSRF, and close sessions deterministically.
3. **Authenticate every runtime route before accepting credentials or commands:** bind/publish the service only on the intended private control plane, enforce request authentication/authorization in code or a documented trusted proxy, and test denial paths. CORS is not authorization.
4. **Identity comes from hardware, not location:** bind a config to verified MAC plus host UID where available, channels to camera UID where available, detect mismatch, prevent duplicates, and update addresses without entity replacement.
5. **Configuration is transactional:** validate a replacement connection and identity first; retain the previous working config/client on failure; represent credential failure as reauth rather than generic offline.
6. **No unsafe mutation by default:** capability-negotiate every control, require exact target/config/channel match, validate bounded parameters, classify risk, preserve idempotency where possible, and deny unknown methods/parameters.
7. **Events are edge-safe:** establish an initial baseline without firing, deduplicate transitions, validate webhook source/payload/size, renew and recover subscriptions, and use polling only as a bounded fallback.
8. **Offline is not empty:** distinguish host unavailable, channel offline, stale, sleeping battery, privacy mode, and authentication failure; preserve last-known inventory while unavailable and avoid add/remove churn after one failed poll.
9. **Battery devices must not be awakened by generic polling:** negotiate sleep/battery support and use push/wake-aware schedules with documented maximum wake frequency.
10. **Diagnostics are useful but shareable:** redact host/IP, usernames, IDs, URLs, credentials, tokens, payloads, and user-defined names by default while retaining model/hardware/firmware, protocol status, last success/error category, subscription state, and capability summaries.
11. **Local means local:** normal operation must not require Reolink cloud or internet. Any optional internet use (for example firmware lookup) must be explicit, separately consented, timeout-bounded, and non-blocking.
12. **Firmware is never an incidental automation:** firmware installation and account administration remain excluded until a separately reviewed, confirmation-gated design exists.

## Prioritized work

### P0 — required before Bronze or broader rollout

1. **Remove/downgrade the Bronze claim and narrow marketplace wording.** Keep beta/1%; describe the exact read-only host inventory slice and change `offline_support` wording so “full” cannot imply media/events/controls.
2. **Implement transactional setup, setup-time verification, reauth, and safe reconfigure.** Classify invalid credentials, non-admin/insufficient privilege, incompatible password, unsupported/account devices, privacy mode, firmware requirement, timeout, and unreachable host. Never replace a working config until validation succeeds.
3. **Adopt stable identity and duplicate prevention.** Persist verified MAC/host UID; use camera UID with a documented fallback; migrate existing host/channel IDs; test DHCP address and interface changes, NVR channel reorder, replacement-device mismatch, and duplicate configuration.
4. **Prove the credential boundary.** Add/enforce route authorization, document trusted network binding, test unauthorized requests, redact host/user/IDs in shareable surfaces, and add broad encoded-secret/log/diagnostic/event assertions. Decide and document HTTP/HTTPS behavior and certificate policy.
5. **Fix availability semantics.** Publish per-channel state; retain inventory through transient failures; model `unavailable`, `stale`, `sleeping`, privacy, and auth separately; emit deduplicated lost/restored transitions; use bounded exponential backoff and isolate host polling so one timeout cannot block all configs.
6. **Make polling capability-aware.** Remove unsafe user-selectable 10-second generic polling or constrain it by model; add battery wake safeguards; document update behavior. Push can be later, but battery devices must be excluded until safe.
7. **Pin and qualify the owning library deliberately.** Evaluate the 0.21.18→0.23.1 delta, pin the exact tested version, inject/share the HTTP session where the runtime supports it, add compatibility fixtures, and automate dependency update review. Do not simply widen the range.
8. **Complete Bronze docs/tests/assets.** User installation/removal, prerequisites and fields, refresh action, trigger/condition, limitations, supported slice, troubleshooting; reviewed brand assets; error/recovery/duplicate/config tests; measured coverage; container build in PR CI.
9. **Produce real release and hardware evidence.** At minimum qualify one standalone powered camera, one doorbell, one supported NVR with multiple channels, address change, disconnect/reconnect, bad credentials/reauth, restart/config restore, and a no-internet run. Publish model, hardware version, firmware, protocol path, test date, and redacted result. Battery/dual-lens/Home Hub stay unsupported until separately tested.

### P1 — useful camera integration after P0

1. Implement a private snapshot/stream broker with fluent/main capability negotiation, authenticated proxying, bounded sessions, concurrency/timeout limits, SSRF protections, and no raw URL exposure.
2. Add motion/AI/visitor events in a proven fallback order: Baichuan TCP push, constrained webhook where required, ONVIF push/long-poll, then bounded polling. Include baseline suppression, transition deduplication, renewal, restart recovery, and representative fixtures/hardware.
3. Expand device/state surfaces based only on negotiated capabilities: channel online, firmware/hardware, battery/charging/sleep, Wi-Fi, and recording/IR/light/LED state. Keep metadata and state semantics distinct.
4. Add useful redacted diagnostics, model/firmware support matrix, known limitations, last-success/error/subscription telemetry, and operator troubleshooting.
5. Handle dynamic channels/chimes without transient deletion, and define explicit stale-device/user-removal policy.

### P2 — controls and parity, only after reliability/security gates

1. Add low-risk controls incrementally (IR, status LED, floodlight), then siren/PTZ/auto-track with capability checks, bounded inputs, exact target validation, confirmation/risk policy, and real-hardware tests.
2. Add recordings/media browsing, two-way audio, chimes, dual-lens logical streams, and battery/Home Hub variants only with broker limits and model-specific qualification.
3. Consider firmware availability reporting separately from installation. Keep firmware install, account administration, arbitrary upstream method execution, factory reset, and unbrokered streams excluded unless independently threat-modeled and approved.
4. Add automatic local discovery/address updates and repair guidance once stable hardware identity is established.
