# PiPhi Modbus vs Home Assistant Modbus: quality and capability comparison

**Assessment date:** 2026-11-13
**PiPhi baseline:** pre-implementation repository at `8c4dc844ee51f8282382a2fb3d60f5978cb91a9f`; the prioritized matrix guided the Modbus parent and RTU-sidecar implementation in this change
**Home Assistant baseline:** `home-assistant/core` `a0f0cf28fea4e1dfea7937305808a3b5414111fd` (2026-11-13) and the current official integration documentation retrieved on 2026-11-13.[HA-CORE][HA-DOC]

## Executive conclusion

Home Assistant is the capability baseline: its generic YAML integration implements TCP, UDP, RTU-over-TCP, serial RTU and serial ASCII; four standard data areas; seven entity platforms; broad numeric/string/custom decoding; byte/word swaps; scaling; polling; writes; connection serialization; retries; and operational connection inventory.[HA-DOC][HA-CONST][HA-SCHEMA][HA-HUB][HA-ENTITY][HA-WS]

PiPhi's **implemented** network slice is much narrower: one explicitly configured, zero-based holding-register address, read with function 03 as one unsigned 16-bit value from a local TCP endpoint. It opens a fresh TCP connection per read, polls no faster than 60 seconds, and deliberately has no write path.[P-TCP][P-STATE][P-README] The RTU sidecar is presently a scaffold, not an operational Modbus serial transport: its configuration/profile schema and isolated CRC, queue, event-redaction and bearer-auth primitives exist, but no code opens a serial port, transmits a frame, polls a register, or connects those primitives to `/command`; configuration currently sets `connected: true` without hardware I/O.[S-SCHEMA][S-TRANSPORT][S-STATE][S-COMMAND]

This does **not** mean PiPhi should copy Home Assistant's unrestricted address-based write services. PiPhi's strongest quality direction is its explicit profile/allow-list boundary, local-endpoint restriction, production fail-closed sidecar authentication, bounded queue/backpressure primitive, redacted event model, and explicit exclusion of raw frames, arbitrary addresses, broadcast writes, destructive diagnostics and untrusted profiles.[P-TCP][S-AUTH][S-TRANSPORT][P-CATALOG][S-CATALOG] Those should be preserved and completed while parity is pursued at the safe semantic-profile layer.

## Scope and scoring rules

- **Implemented** means reachable production behavior, not a manifest claim, README statement, schema alone, catalog item, or unit-tested but unwired helper.
- **Parity target** means a generally useful Home Assistant capability PiPhi should support through bounded profiles.
- **PiPhi advantage** means a quality property worth retaining even where it intentionally prevents literal API parity.
- Home Assistant's generic Modbus YAML surface is a useful capability comparator, not a safety ideal. Its `write_register` and `write_coil` actions accept caller-selected unit/address/value on an existing hub; Home Assistant protects service registration with its own platform permissions, but the Modbus layer does not constrain those writes to a device profile.[HA-SERVICE]
- Modbus itself defines request/reply function codes and the four data areas; semantic types, scale, units, and device-specific writable ranges come from device documentation/profiles rather than the base protocol.[MB-SPEC]

## Detailed comparison

| Area | Home Assistant current behavior | PiPhi parent + RTU sidecar current behavior | Assessment / target |
|---|---|---|---|
| **Transports** | YAML hubs support TCP, UDP, RTU-over-TCP, serial RTU and serial ASCII. The newer shared-connection API also models TCP, UDP, TLS and serial parameters for device-specific integrations.[HA-DOC][HA-SCHEMA][HA-CONNECTION] | Parent implements Modbus TCP only. It limits hosts to private/link-local/loopback IPs or `.local`/`.lan` names and defaults to port 502. Sidecar declares RTU/ASCII but has no serial dependency or serial I/O implementation.[P-TCP][S-PROJECT] | **Large gap.** P0: make RTU operational; P1: robust persistent TCP. UDP/RTU-over-TCP/ASCII are demand-driven P2. TLS should be profile/deployment driven; do not weaken the local-network rule merely for parity. |
| **Configuration / profile model** | Generic YAML is per hub and per entity: connection settings plus raw unit, address, register type and decode settings. Device-specific integrations may use their own UI config flows while sharing connections. YAML reload is supported.[HA-DOC][HA-SCHEMA][HA-CONNECTION][HA-SERVICE] | Parent config identifies a host and optional single address/unit. Sidecar has a promising `RegisterProfile` with stable ID, unit/address, `uint16`/`int16`, unit, scale, offset, writable and min/max; up to 256 unique targets. Parent does not consume it, sidecar config is not parent-owned in practice, and startup snapshot sync is a no-op.[P-SCHEMA][S-SCHEMA][P-LIFECYCLE][S-LIFECYCLE] | **Profile governance is the intended PiPhi advantage, but not yet realized.** P0 requires a versioned, provenance-bearing parent profile compiled into sidecar requests; reject unknown points and profile drift. |
| **Point and entity types** | Reads coils, discrete inputs, input registers and holding registers. Platforms are binary sensor, sensor, switch, light, fan, cover and climate, including mode/status mappings and device classes.[HA-CONST][HA-SCHEMA][HA-DOC] | Parent exposes only `connected`, raw `holding_register_value`, and `refresh`. Sidecar exposes only service-level `connected`/`refresh`; profile entries do not become entities.[P-MANIFEST][S-MANIFEST] | **Large gap.** P0 should cover typed sensor/binary sensor points and safe switch/setpoint commands. Rich climate/cover/light/fan composites are P1/P2 according to qualified profiles, not generic guesses. |
| **Data types, endianness, scaling** | `int16/32/64`, `uint16/32/64`, `float16/32/64`, string and custom `struct`; byte, word, or word+byte swaps; scale and offset; precision; NaN, clamp and zero-suppression handling.[HA-CONST][HA-SCHEMA][HA-ENTITY] | TCP is fixed big-endian unsigned 16-bit with no scale/unit. Sidecar schema has `uint16`/`int16`, scale/offset/unit/min/max, but no decoder is called and there is no width or endianness model.[P-TCP][S-SCHEMA] | **Large gap.** P0 needs deterministic profile decoding for signed/unsigned 16/32-bit and float32, explicit byte/word order, scale/offset/unit/bounds, and fixture vectors. Add 64-bit/string/enums/bitfields only with device demand. Do not accept arbitrary Python `struct` strings from untrusted users. |
| **Polling and batching** | Default per-entity interval is 15 s; `0` disables periodic polling. Requests serialize behind a hub lock and optional inter-message delay. `virtual_count` can read contiguous binary/sensor values in one request, but there is no general planner that coalesces arbitrary adjacent YAML entities.[HA-DOC][HA-HUB][HA-ENTITY][HA-SENSOR] | Parent polls serially through all entries every five seconds when due, but clamps each configured interval to at least 60 s. Every point creates a new TCP connection and reads quantity 1. Failed reads receive a default next attempt around five minutes later because failure does not set the configured `next_poll_at`. Sidecar's bounded one-at-a-time queue is tested but unused.[P-STATE][P-TCP][S-TRANSPORT] | **Large efficiency/recovery gap.** P0 needs per-bus serialization and bounded load. P1 needs contiguous poll-block planning, configured cadence on both success/failure, jitter, stale quality, partial-block isolation, and metrics. |
| **Writes and actions** | Entity writes cover coils/registers and single/multiple writes. Admin-independent Modbus actions expose arbitrary unit/address/value writes on configured hubs; toggle entities may perform read-back verification.[HA-HUB][HA-SERVICE][HA-ENTITY] | Parent never emits a write function. Sidecar `writable`, min and max fields are inert; `/command` only records a refresh event and does no transport work.[P-TCP][S-SCHEMA][S-STATE] | **Intentional non-parity today; safe writes are a P0 functional gap for control use cases.** Add only named profile commands with exact unit/address/function, type/range/enum constraints, authorization, idempotency policy where applicable, read-back/confirmation, audit event and broadcast prohibition. Never add raw PDU or arbitrary-address services. |
| **Validation and safety** | Strong schema validation catches conflicting fields, type/swap/count errors and platform options. Runtime serializes requests and marks entities unavailable on errors. Generic writes remain broad once a hub exists.[HA-SCHEMA][HA-VALIDATORS][HA-ENTITY][HA-SERVICE] | Parent validates address `0..65535`, unit `1..247`, response transaction/protocol/unit/length/function/byte count, five-second I/O bounds, and rejects nonlocal/ambiguous hosts. Sidecar validates profile IDs, line settings, uniqueness, nonzero scale, CRC/unit/function/exception responses, and queue capacity, but most serial checks are not wired.[P-TCP][S-SCHEMA][S-TRANSPORT] | **PiPhi advantage in fail-closed scope, incomplete in depth.** Keep local-target and profile constraints. P0 must add overlap/width checks, finite numeric constraints, writable bounds, read-only area enforcement, max PDU quantities, serial timing/frame limits, and transactional config rejection. |
| **Reconnect / error handling** | YAML hubs retry initial connection every 60 s, configure three pymodbus retries, serialize calls, suppress duplicate error logs, close cleanly, and mark entities unavailable on read/write failures. Shared connections are reference-counted, reject incompatible settings, and close on last release/shutdown.[HA-HUB][HA-CONNECTION][HA-ENTITY] | TCP creates and closes each connection per poll, so the next poll inherently reconnects; there is no retry/backoff, persistent session, per-error classification, or recovery event. Sidecar declares reconnect ownership but does not open hardware. Worse, sidecar config reports connected immediately.[P-TCP][P-STATE][S-STATE][S-README] | **P0 correctness gap:** never report connected without a successful protocol transaction (serial port “open” should also be distinct from unit responsive). Add bounded exponential backoff/jitter, per-unit health, stale timestamps, recovery transitions, and restart reconciliation. |
| **Diagnostics / observability** | Admin-only WebSocket inventory lists endpoint, connection state, source and unit users; official UI explains that serial “open” does not prove a unit answers. Logs identify device/address failures, and entities expose availability.[HA-WS][HA-DOC][HA-HUB] | Both services expose common health/diagnostics and event endpoints. Parent reports config IDs/event counts and generic state; warning logs intentionally omit endpoint details. Sidecar has useful sanitization and replay-gap primitives, but runtime diagnostics do not use its `EventBuffer`, queue stats, CRC counters or serial status.[P-HEALTH][S-HEALTH][S-TRANSPORT] | **Mixed.** PiPhi's structured/redacted event direction can exceed HA. P0/P1 must expose secret-free transport/unit/point quality, last success, error taxonomy/counters, queue depth/high-water mark, poll duration, reconnect count, profile hash, dropped-event/gap status and transition events. |
| **Security / authentication boundary** | Official docs explicitly warn that ordinary Modbus TCP has no client authentication or encryption and must be isolated on a trusted network. The integration manifest is local polling. Admin is required for the connection inventory; HA services operate inside HA's authenticated service boundary.[HA-DOC][HA-MANIFEST][HA-WS] | Parent narrows network destinations to local addresses and excludes `api_key` from stored entry config, but speaks plaintext Modbus TCP. Sidecar middleware uses constant-time bearer comparison and fails closed in production when no token is configured, but protects only `/command` and `/v1/modbus/*`; no `/v1/modbus/*` transport API exists yet, and config/state routes are not covered by this middleware.[P-TCP][P-STATE][S-AUTH][S-APP] | **Potential PiPhi advantage.** P0 must authenticate every parent-to-sidecar control/config/request route, bind/expose sidecar only on the internal container network, inject secrets rather than store them in profiles, and threat-test route coverage. Device-side Modbus remains trusted-segment traffic unless profile-supported Modbus Security/TLS is implemented.[MB-SPEC] |
| **Test quality** | The examined core tree has 152 test functions across schema/setup, all seven platforms, decoding, polling, writes/services, deprecations, shared connection lifecycle and WebSocket inventory. Tests include connection sharing/conflicts, shutdown/exception cleanup and reconnect-on-reload behavior.[HA-TESTS] | The two PiPhi packages have 31 test functions, many for generic manifest/contract conformance. Parent has focused MBAP request/response, exception, host restriction and fail-closed state tests. Sidecar tests CRC validation, queue saturation, replay gaps, redaction and bearer failure, but there is no serial emulator/PTY test, parent↔sidecar test, polling/batching test, write test or restart test.[P-TEST][S-TEST] | **Large maturity gap.** P0 requires end-to-end protocol tests, malformed/timeout cases and real command-path assertions. P1 requires property/fuzz tests and broader protocol fixture coverage. Test count is only a breadth indicator, not a quality score. |
| **Deployment architecture** | Modbus runs in the HA process. Generic YAML hubs own clients; newer device integrations can share a reference-counted physical connection via a common library. Direct serial access therefore sits in the HA process/container.[HA-HUB][HA-CONNECTION] | Parent and serial sidecar are separate Python containers with separate runtime contracts and restart policies. The intended split places semantics/entities in the parent and privileged serial ownership/arbitration in the sidecar.[P-DOCKER][S-DOCKER][S-README] | **PiPhi-specific architectural advantage if completed:** smaller serial-device privilege boundary, independent recovery, and one bus owner. P0 must make the split real, with a narrow authenticated typed RPC, exclusive device mapping/locking and startup reconciliation. |
| **Compatibility evidence** | Official docs describe USB-RS485 adapters, serial servers and gateways, but the generic integration does not require or publish a certified adapter/device matrix.[HA-DOC][HA-MANIFEST] | Compatibility is established through protocol conformance, attributed device-document fixtures, PTY-backed RTU simulation, malformed-frame recovery, and multi-architecture container tests.[P-TEST][S-TEST] | Follow Home Assistant's generic-integration model: physical adapter/device certification is not a release or rollout gate. Document protocol and profile limits accurately and expand fixtures when compatibility defects are reported. |

## Prioritized gap matrix

Priority means release risk, not implementation order within a sprint.

| Priority | Gap / deliverable | Why | Concrete acceptance criteria |
|---|---|---|---|
| **P0** | **Truthful RTU transport and parent↔sidecar path** | The sidecar currently reports connection without I/O and does not perform Modbus. | (1) A typed, authenticated request from parent reaches the sidecar and performs FC01/02/03/04 against a PTY/device simulator; (2) one request at a time per bus; (3) valid CRC/LRC and timing enforced; (4) timeout, bad CRC, wrong unit/function and Modbus exception are distinct typed failures; (5) `service_available`, `port_open`, and `unit_responsive` are separate states; (6) no successful transaction means no `connected: true`; (7) hot-unplug and restart recover without process restart; (8) broadcast writes and arbitrary frames are impossible through the API. |
| **P0** | **Versioned semantic profile contract** | Safe point coverage depends on trusted semantics. | (1) Signed profile artifact has ID/version/hash/provenance; (2) exact unit, area, address, width, type, byte/word order, scale, offset, unit and access mode per point; (3) duplicate IDs, overlapping incompatible ranges, non-finite scale/offset/bounds, out-of-range widths and writable read-only areas fail atomically; (4) parent owns profile selection and sidecar accepts only compiled allow-listed requests; (5) applied profile hash appears in state/diagnostics/audit events; (6) no arbitrary address/PDU escape hatch. |
| **P0** | **Baseline reads and entities** | One raw holding register is not useful parity. | (1) Coils, discrete inputs, input registers and holding registers work over TCP and RTU; (2) boolean, int16/uint16, int32/uint32 and float32 decode with explicit ABCD/BADC/CDAB/DCBA policies; (3) scaling/offset/unit/bounds and enum mapping are deterministic; (4) sensor and binary-sensor entities carry timestamp, availability and quality; (5) golden vectors cover minimum, maximum, negative, NaN/invalid (where relevant), every endianness and malformed short responses. |
| **P0** | **Bounded polling and recovery** | Current TCP polling is one connection/point and failure cadence is inconsistent; serial has no poller. | (1) Persistent connection/session per endpoint/bus where supported; (2) all requests serialized per physical link; (3) configurable poll interval with documented floor; (4) bounded queue and per-profile request-rate/quantity limits; (5) bounded retry then exponential backoff with jitter; (6) failed points become stale/unavailable without replacing the last value with fabricated data; (7) one failed block does not suppress unrelated blocks; (8) tests prove recovery after disconnect, timeout, sidecar restart and queue saturation. |
| **P0** | **Safe semantic writes** | Control is a core capability, but literal HA raw-write parity would violate PiPhi's safety model. | (1) Only named profile actions can write; (2) exact function/unit/address/type and min/max/enum are immutable at invocation; (3) per-action authorization and audit identity; (4) no unit 0/broadcast; (5) write timeout/error is surfaced; (6) required actions read back and compare within configured tolerance/deadline; (7) retry/idempotency policy is explicit per action and never blindly repeats a non-idempotent pulse; (8) tests prove attempts to override address/function/range are rejected before transport. |
| **P0** | **Complete internal security boundary** | The sidecar will own a privileged serial device. | (1) Every mutating/config/request route is authenticated; state/diagnostics exposure is explicitly classified and either authenticated or network-isolated; (2) production startup fails if token/identity is missing; (3) token rotation works without profile edits and tokens never enter logs/events/diagnostics; (4) sidecar has no host-published port and receives only explicit serial device mappings; (5) tests enumerate all routes and prove unauthorized requests cannot configure, read, write or infer sensitive port paths; (6) container runs non-root with least filesystem/device permissions where the platform permits. |
| **P1** | **Contiguous block planner and scheduler** | Necessary for scale and bus health; HA only partly batches through virtual counts. | (1) Planner coalesces compatible adjacent points without crossing function/unit, profile maximum gap, protocol quantity limits or unsafe holes; (2) decoder maps partial blocks deterministically; (3) configurable poll groups/priorities; (4) fairness prevents command or slow-unit starvation; (5) request-count reduction is measured against one-point reads; (6) planner property tests prove no out-of-profile address is read. |
| **P1** | **Operational observability** | Structured, redacted diagnostics can be a PiPhi quality advantage. | State/diagnostics expose profile hash, redacted endpoint/port identity, queue depth/capacity/high-water mark, per-unit last success, point age/quality, poll duration/success/failure, exception/CRC/timeout/reconnect counters and event-buffer dropped/gap status; online/offline/degraded/recovered and queue transitions emit once per transition; no secrets, raw frames or full serial paths appear. |
| **P1** | **Test depth and release gates** | Helpers passing in isolation does not establish a working integration. | CI runs parent↔sidecar integration tests with TCP simulator and Linux PTY serial simulator; covers all supported functions/types/orders, cancellation, saturation, malformed/truncated frames, exception codes, reconnect/restart and auth route coverage; fuzz/property tests target MBAP/RTU parsers and block planning; coverage is reported for protocol modules; release is blocked on contract, integration and security suites. |
| **P1** | **Protocol compatibility corpus** | Generic Modbus compatibility depends on deterministic framing and profile interpretation rather than vendor certification. | Retain attributed fixtures for representative meters, relays and HVAC controls; test line settings, timing boundaries, malformed responses, reconnects and supported function/type combinations against TCP and PTY simulators; add regression fixtures for reported compatibility defects. |
| **P1** | **Composite device entities** | HA users expect semantic controls, not register cards. | At least one reviewed profile maps points/actions into a switch and one setpoint/thermostat-like entity with verified state, limits, units and availability. Composite state transitions and write confirmation are tested against deterministic simulators and attributed fixtures. |
| **P2** | **Additional data types and transforms** | Useful but should follow device demand. | Add int64/uint64/float64, fixed strings, bitfields/counters and derived rates only through reviewed profile schema; each has golden vectors, overflow/wrap/encoding rules and no executable/custom format strings. |
| **P2** | **Additional transports** | HA has broader generic reach, but low-use transports should not delay core quality. | RTU-over-TCP, ASCII and UDP are each enabled only with transport-specific framing, timing/reconnect tests and representative protocol fixtures. Modbus Security/TLS, if added, validates certificates and identity and does not silently downgrade. |
| **P2** | **Richer semantic composites and diagnostics** | Climate, fan, light, cover and safe standard diagnostic functions are device-specific. | Each capability is profile-declared, range/state mapped and fixture-tested. Only non-destructive allow-listed diagnostics are exposed; listen-only, counter clearing, communications restart, vendor functions and raw PDUs remain excluded unless a separate privileged, audited engineering product is deliberately designed. |

## Recommended quality stance

1. **Match HA's useful coverage, not its raw surface.** Target the four data areas, common types, robust connection handling, efficient polling and semantic entities. Do not target arbitrary unit/address writes, custom executable unpack formats, raw PDUs or broadcasts.
2. **Make profiles the only semantic authority.** Device manuals and attributed fixtures should produce reviewed profile artifacts; transport code should know framing and bounds, not device meaning.
3. **Keep the sidecar narrow and privileged.** It should own allow-listed serial devices, exclusive bus arbitration, framing/timing and typed requests. Parent owns profiles, entities, policy and user authorization.
4. **Treat quality metadata as a deliverable.** Availability must distinguish process, link and unit; every value needs age/quality; every write needs outcome/audit; every release needs simulator evidence and an explicit supported protocol/profile scope.
5. **Do not advertise planned catalog groups as product capability.** The present catalogs correctly label most work planned/excluded, but manifests and UI should expose only transport paths exercised by the same release's end-to-end tests.[P-CATALOG][S-CATALOG]
