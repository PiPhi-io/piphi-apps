# Home Assistant quality comparison: PiPhi pfSense and MikroTik RouterOS

**Research cutoff:** 2026-11-16

**PiPhi revision audited:** [`e3eb2d3`](https://github.com/PiPhi-io/piphi-apps/tree/e3eb2d3084645ab2cf4f80e925368b28f6fdb27e)

**Home Assistant Core revision audited:** [`7682317`](https://github.com/home-assistant/core/tree/76823177f8d296dbbf017fe59627757b695e71d5)

**Home Assistant documentation revision audited:** [`b86ad88`](https://github.com/home-assistant/home-assistant.io/tree/b86ad8850f807f39580b5a6636967d96178f1214)
**pfSense REST API revision consulted:** [`82ff327`](https://github.com/pfrest/pfSense-pkg-RESTAPI/tree/82ff3272b27b5dfc959d543e3fa3f3010187355d)

## Executive conclusion

These integrations must not share a quality claim merely because both administer network appliances.

- **pfSense is a meaningful monitoring implementation, but not release-qualified for a production firewall.** It authenticates to the unofficial community pfSense REST API v2, verifies TLS by default, validates a required system read before accepting configuration, projects broad operational state, closes clients/tasks, and places every mutation behind a default-off feature gate and exact allowlist. Its principal release blockers are the unsupported upstream package boundary; no tested firewall/API compatibility matrix; host-derived identity; raw network/security data exposure; no retry, backoff, jitter, rate control, or stale-age model; and a dangerous correctness detail where every endpoint except `/status/system` is treated as optional, including the documented baseline endpoints. No first-party Home Assistant pfSense integration exists at the audited revisions, so this report does **not** manufacture one as a comparator. Home Assistant SNMP, UPnP, Wake-on-LAN, or generic device trackers are not direct substitutes for this pfREST feature surface.
- **MikroTik is an honest two-metric transport slice in code, but its manifest materially overclaims it.** The implementation performs one authenticated, certificate-verified HTTPS `GET /rest/system/resource`, validates CPU/memory values, has no RouterOS mutation path, and reports failures without returning the password. It does not monitor interfaces or clients, discover routers, work offline, support RouterOS 6 through REST, derive device identity, qualify hardware/firmware, or implement meaningful diagnostics/reconfigure/reauth. The manifest nevertheless claims interfaces, clients, controls, local discovery, onboarding by discovery, and full offline support. These claims are P0 defects.
- **The direct first-party comparison is Home Assistant's MikroTik integration only.** HA's current integration is declared **Gold**, uses the RouterOS binary API, supports RouterOS 6 and 7, connects before save, reauthenticates/reconfigures, polls every 10 seconds, discovers dynamic clients across DHCP/wireless stacks, models away timing, exposes system/interface/PoE/update/maintenance entities, removes stale interface devices, and documents a least-privilege `read,api,test` user ([manifest](https://github.com/home-assistant/core/blob/76823177f8d296dbbf017fe59627757b695e71d5/homeassistant/components/mikrotik/manifest.json), [quality file](https://github.com/home-assistant/core/blob/76823177f8d296dbbf017fe59627757b695e71d5/homeassistant/components/mikrotik/quality_scale.yaml), [documentation](https://github.com/home-assistant/home-assistant.io/blob/b86ad8850f807f39580b5a6636967d96178f1214/source/_integrations/mikrotik.markdown)). PiPhi intentionally has a much narrower and safer read-only surface today, but is far below that operational maturity.

Both packages are appropriately `draft`, rollout `0`, and qualification `unverified`. Keep them there until the P0 work and hardware/version qualification are complete.

## Scope and method

The audit inspected executable clients, schemas, lifecycle, routes, state projection, manifests, catalogs, tests, package locks, Dockerfiles, centralized CI/release workflows, and local release tags. External claims use owning-project sources: Home Assistant Core/docs, MikroTik RouterOS documentation, Netgate documentation, and the pfREST project itself. Home Assistant's Integration Quality Scale (IQS) is applied **analogically**; PiPhi packages are not HA Core integrations and cannot literally earn an HA tier.

“Direct comparator” means the same vendor/protocol/product function. The first-party HA MikroTik integration qualifies. There is no first-party HA pfSense integration at the audited revisions. A third-party/custom HA pfSense component is outside this audit, and generic SNMP/UPnP/router integrations are not treated as feature parity.

## Honest supported slices

### pfSense

The executable slice is:

1. manual host/API-key configuration against the **unofficial community** pfREST v2 package;
2. HTTPS with normal certificate/hostname validation by default, optional private CA, and explicitly configurable insecure HTTP or disabled verification;
3. a required system read plus parallel polling of version, interfaces, gateways, and services, with optional DHCP/ARP client inventory, VPN, certificate-expiry metadata, logs, and CARP/HA status;
4. normalized telemetry/entities and transition events, with interface rates derived from counters;
5. immediate refresh; and
6. default-off exact-allowlisted ping, service start/restart, and preconfigured Wake-on-LAN.

It is **not** a Netgate-supported API integration, firewall-policy manager, package manager, backup/restore tool, VPN secret manager, or configuration editor. Its discovery endpoint merely echoes a supplied/default hostname; it does not discover or identify a firewall ([discovery](https://github.com/PiPhi-io/piphi-apps/blob/e3eb2d3084645ab2cf4f80e925368b28f6fdb27e/apps/integrations/piphi-network-pfsense/src/piphi_network_pfsense/routes/discovery.py#L17-L37)). The upstream project itself says the package is unofficial and unsupported by Netgate and warns that unsupported pfSense versions may be unstable ([upstream README](https://github.com/pfrest/pfSense-pkg-RESTAPI/blob/82ff3272b27b5dfc959d543e3fa3f3010187355d/README.md#disclaimers)). Netgate likewise distinguishes third-party software from the pfSense system and warns that alternate-repository package compatibility cannot be predicted across upgrades ([third-party software](https://docs.netgate.com/pfsense/en/latest/book/thirdparty.html), [upgrade notes](https://docs.netgate.com/pfsense/en/latest/install/upgrade-guide-versions.html)).

### MikroTik RouterOS

The executable slice is only:

1. manual host, username, password, and optional CA bundle;
2. HTTPS-only Basic authentication to `GET /rest/system/resource`;
3. strict parsing of CPU load and used-memory percentage;
4. polling no faster than 60 seconds after a successful read; and
5. a `refresh` action that repeats that read.

There are no writes. There is also no interface state, traffic, clients/device tracking, DHCP/ARP/wireless data, firmware/version/serial identity, discovery, offline operation, or controls. RouterOS documents REST as a JSON wrapper introduced in v7.1beta4, requiring `www-ssl`/`www`, using Basic Auth, and exposing CRUD plus arbitrary console commands; it explicitly advises against HTTP because credentials can be passively captured ([REST API](https://help.mikrotik.com/docs/spaces/ROS/pages/47579162/REST+API), last updated 2025-08-12). PiPhi's HTTPS-only fixed resource URL is therefore a sound narrow boundary.

## Analogical IQS assessment

The current HA IQS requires every rule in a tier and all tiers below it. HA's MikroTik integration declares **Gold** and its rule file marks config-flow testing, test-before-configure/setup, unique entries, unload, unavailable state, logging, reauth, coverage, diagnostics, dynamic/stale devices, reconfigure, and user documentation complete; only async dependency and strict typing remain for Platinum ([quality file](https://github.com/home-assistant/core/blob/76823177f8d296dbbf017fe59627757b695e71d5/homeassistant/components/mikrotik/quality_scale.yaml)). This is evidence about HA MikroTik only, not a transferable rating.

### PiPhi pfSense: below Bronze / not tier-eligible

Positive analogues: live test-before-configure, async I/O, typed config, teardown, entities, useful docs, dependency transparency, safe default action gates, optional-endpoint degradation, and substantial functional tests. Bronze remains blocked by unstable host identity/duplicate handling, synthetic discovery, inconsistent “read-only” claims, incomplete baseline privilege enforcement, absent reauth/reconfigure semantics, and no release/hardware support evidence. Silver is blocked by stale/unavailable semantics, retry/concurrency policy, action postconditions, and lack of coverage enforcement. Gold is blocked by redacted diagnostics, privacy controls, stable device identity, stale-device policy, repairs, and qualified supported-device/version documentation.

### PiPhi MikroTik: below Bronze / not tier-eligible

The fixed read-only HTTPS endpoint, truthful connectivity-after-I/O, strict parser, secret omission tests, teardown, and fail-closed command catalog are good seeds. Bronze is blocked by save-on-failed-configure, no stable identity/duplicate prevention, false discovery/offline/interface/client/control claims, no exact privilege instructions, no supported-version negotiation, and placeholder entity metadata. Silver is blocked by generic errors, no reauth, retry storm behavior, sequential polling, no unavailable/stale timestamps, and low functional coverage. Gold is blocked by essentially every device-tracking, diagnostics, reconfigure, dynamic-device, stale-device, translation, and documentation expectation demonstrated by HA MikroTik.

## Security invariants

These are release gates for a network-administration domain:

1. **No false capability or connectivity.** “Connected” requires a fresh authenticated response from every endpoint designated essential for the selected profile. Planned interfaces/clients/controls/discovery/offline support must not appear in released metadata.
2. **TLS is the production floor.** HTTPS with hostname and chain verification stays default; insecure HTTP or disabled verification must be lab-only, visibly unsafe, and impossible to enable accidentally. CA files must come from an approved read-only mount.
3. **Least privilege is explicit and testable.** Publish exact pfREST endpoint privileges and exact RouterOS custom policies plus source-address restriction. Never recommend RouterOS's built-in `read` group as least privilege.
4. **No arbitrary administration.** No caller-supplied URL/path, RouterOS console word, shell/script, firewall/NAT/route/DNS/user/VPN secret, package, backup/restore, capture, factory reset, or update primitive.
5. **Mutations are separately enabled and exactly targeted.** Every operation needs a typed target, per-operation gate, exact allowlist, single-device scope, authorization, confirmation proportional to impact, serialization, timeout, idempotency classification, and audited postcondition.
6. **Critical network services need a deny-by-default risk model.** DNS, DHCP, routing, VPN, HA, web/API, and authentication services cannot be restartable merely because their names were entered in a generic allowlist.
7. **Bound appliance load.** Bound requests per snapshot, concurrent calls, routers polled concurrently, command rate, payload/response bytes, log rows, retained IDs/events, and retries. Honor server throttling and use exponential backoff with jitter and a circuit breaker.
8. **Identity is appliance-derived.** Derive an opaque stable ID from verified serial/system identity, survive host changes, reject duplicates, and keep raw serial/MAC/host out of telemetry and support bundles by default.
9. **Unknown and stale remain explicit.** Missing permissions, unsupported fields, absent packages, timeouts, counter resets, and stale leases must never become zero, false, offline, or healthy without an explicit reason and observation timestamp.
10. **Network-client privacy is opt-in.** MACs, IPs, hostnames, SSIDs, lease data, remote VPN endpoints, CARP addresses, and presence history require minimization, opaque IDs where possible, retention limits, and documented deletion behavior.
11. **Logs are hostile sensitive input.** Bound and sanitize them before parsing, hashing, logging, diagnostics, events, or UI. Never forward raw auth/firewall log text by default; redact credentials, tokens, query strings, public IPs, usernames, and hostnames.
12. **Secrets never cross observability surfaces.** API keys/passwords, Basic Auth headers, CA/private material, VPN keys, certificate bodies, HA-sync passwords, and secret-bearing upstream errors never enter state, telemetry, events, logs, diagnostics, idempotency records, or fixtures.
13. **Failures are classified, not replayed blindly.** Authentication/certificate/permission/schema/version failures require user action and must not retry every few seconds. Only bounded transient network/server failures retry automatically.
14. **No unqualified release.** A release requires immutable source/image digest, SBOM/provenance, container smoke test, coverage/type/lint gates, and a published hardware/firmware/API/package matrix with upgrade and rollback evidence.

## Prioritized work

### P0 — truthful and safe before publication

1. **MikroTik:** correct manifest/marketplace/runtime claims to manual configuration, online-only CPU/memory health over RouterOS 7 REST; remove interfaces, clients, controls, local/passive discovery, discovery onboarding, RouterOS API, `demo-device`, and `offline_support: full`. Mark `api_key` as a secret and rename it `password` with migration handling.
2. **MikroTik:** make configuration fail on connection/auth/TLS/version errors; classify errors; implement reauth/reconfigure; set `next_poll_at` on failure with bounded exponential backoff+jitter so outages do not trigger a request every five seconds.
3. **pfSense:** define selected-profile essential endpoints and fail setup/mark unavailable when they are forbidden or malformed. Do not call a partial baseline snapshot connected. Correct all `read_only` diagnostics/events when any operational mutation is enabled.
4. **Both:** replace host identity with verified appliance-derived opaque identity, reject duplicates, support host change safely, and remove synthetic/passive discovery metadata unless genuine discovery is implemented.
5. **Both:** publish exact least-privilege setup. For RouterOS use a custom REST group and source address; for pfREST map each profile/action to endpoint privileges. Add automated permission-denial matrices.
6. **pfSense:** stop forwarding raw security log text by default; add bounded structured extraction/redaction and explicit privacy opt-in. Redact host/config IDs and network identifiers from exported diagnostics.
7. **Both:** reconcile GHCR publishing metadata with runtime/README image references, enable PR container builds, and keep draft/rollout 0 until qualified evidence exists.

### P1 — resilient monitoring and proof

8. Add per-device serialization, global/per-appliance concurrency limits, response-size/row limits, retry classification, `Retry-After`, exponential backoff with jitter, circuit breakers, last-attempt/last-success/stale-age, offline/recovered transitions, and restart reconciliation.
9. **pfSense:** add TLS/CA/hostname, timeout/cancellation, partial-profile, reconfigure/reauth, concurrent action/poll, command postcondition, counter wrap, lease aging, malformed/oversized payload, and sensitive-log redaction tests. Add service risk tiers and a non-overridable critical-service denylist pending explicit design review.
10. **MikroTik:** add RouterOS version/system identity to the same read-only snapshot, `.proplist` response minimization where supported, a persistent secret lifecycle, useful redacted diagnostics, and deterministic fake RouterOS REST tests for 401/403/404/429/5xx, invalid JSON, certificate failure, disconnect/recovery, and RouterOS field variants.
