# Home Assistant camera quality comparison

**Research cutoff:** 2026-11-15

**PiPhi revision reviewed:** [`e9c7fb55230a5512735f333c7f802e580f81743a`](https://github.com/PiPhi-io/piphi-apps/tree/e9c7fb55230a5512735f333c7f802e580f81743a)
**Scope:** `piphi-camera-stream` 0.1.5, `piphi-webrtc-sidecar` 0.3.5, and `piphi-wyze-camera-service` 0.1.3.

## Executive conclusion

The bundle has a sound **intended separation of responsibilities**: the camera integration retains the saved RTSP secret, Core passes it to an authenticated media API, and the media service creates bounded go2rtc sessions. The implementation backs important parts of that design with constant-time token checks, secret types, response redaction, source URL validation, loopback-only go2rtc control/RTSP listeners, capacity limits, expiry cleanup, codec probing, and pinned upstream container digests. Those are meaningful strengths, not Home Assistant parity claims.

It is **not yet equivalent to the current first-party Home Assistant camera platform experience and is not ready for an HA-IQS-equivalent Bronze claim**. The largest gaps are:

1. **Critical authorization boundary:** the Wyze adapter accepts account credentials at `PUT /v1/wyze-bridge/config` and returns credential-bearing RTSP descriptors from `GET /v1/wyze-bridge/cameras`, but its router has no authentication dependency. Network isolation is only documented, not enforced by this service. This differs from the fail-closed source and media routes elsewhere in the bundle.
2. **Availability is synthetic:** configuring an RTSP URL immediately publishes `connected: true` and `available: true` without opening the source. The `refresh` command only emits an event. Camera or bridge disconnects do not update entity state, and there is no reconnect supervisor or transition logging.
3. **Narrow camera behavior:** PiPhi exposes WebRTC viewing only. It has no still-image contract, snapshot, recording, play-stream/HLS fallback, camera on/off, motion state/events, two-way audio, trickle ICE/candidate API, or session keepalive. Home Assistant's camera contract provides stills and can route one stream source through HLS for recording/playback and through a WebRTC provider for low latency ([HA camera entity](https://developers.home-assistant.io/docs/core/entity/camera); [HA Stream](https://www.home-assistant.io/integrations/stream/)).
4. **Wyze is an adapter, not an end-user integration:** no PiPhi Wyze camera integration in this scope owns account onboarding or creates entities. The service README explicitly assigns that to a future/separate integration. There is no first-party Home Assistant Wyze camera integration against which exact parity can honestly be asserted; the valid comparisons are the HA camera platform contract and the pinned `docker-wyze-bridge` behavior.
5. **Evidence is pre-release:** all three manifests remain `quality_tier: unrated`; qualification is `unverified`; camera publication is `draft`; services are `beta`. Tests are mostly unit/contract fakes, and the Wyze README says hardware qualification requires a real account and camera. Central CI/release workflows exist, but `piphi-camera-stream` is still declared `legacy-static` with no package test commands or PR container build; the two services declare full checks and container builds. Release documentation is also stale or contradictory in places.

**Release recommendation:** keep the bundle unrated and non-general-availability. Do not expose the Wyze API or port 18554 beyond the trusted Core/service network. Close the Wyze authorization gap and add truthful end-to-end availability/reconnect behavior before broader rollout.

## Comparison basis and limits

- Home Assistant's current camera developer contract says every camera serves still images; a stream-capable camera supplies either a stream source or native WebRTC. A stream source is reused by the Stream integration for HLS, `camera.record`, and `camera.play_stream`, while a registered provider such as go2rtc can add WebRTC ([camera entity documentation](https://developers.home-assistant.io/docs/core/entity/camera)).
- HA's Stream integration proxies H.264/H.265 to HLS/LL-HLS and supports AAC/MP3 audio, with explicit browser limitations ([Stream documentation](https://www.home-assistant.io/integrations/stream/)). HA's go2rtc integration is an internal system integration and warns that exposing its debug API is unsafe ([HA go2rtc documentation](https://www.home-assistant.io/integrations/go2rtc/)).
- HA's IQS has 54 cumulative rules: 20 Bronze, 10 Silver, 21 Gold, and 3 Platinum. It is written for integrations inside HA Core, so this report uses it as a **mapping rubric**, not as certification of a PiPhi service ([official IQS rules](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules)).
- WebRTC does not prescribe the signaling channel. The application must exchange offer/answer and ICE control messages, and `iceServers` supplies STUN/TURN information ([W3C WebRTC Recommendation](https://www.w3.org/TR/webrtc/)). Therefore PiPhi's HTTP offer/answer API is valid in principle, but its one-shot SDP design is less complete than HA's current asynchronous answer/candidate/session-close model.
- Wyze officially documents API-key login and refresh, including one-year API-key, two-day access-token, and 30-day refresh-token validity and rate-limit guidance ([Wyze API-key documentation](https://support.wyze.com/hc/en-us/articles/16129834216731-Creating-an-API-Key)). The camera streaming and model support here come from independently maintained `docker-wyze-bridge`, not a first-party Wyze streaming API.

## Feature and behavior gaps

### P0 — security and truthful state

- Require a production bearer/service identity on every Wyze control route; fail closed when absent; bind it to the intended Core/container identity. Add negative tests for configure, deconfigure, cameras, and status. Treat RTSP descriptors as credentials.
- Restrict the Wyze RTSP listener to the minimum reachable service network. A generated global password is better than no auth, but per-consumer/per-camera credentials or a Core proxy would reduce blast radius. Do not publish port 18554 to an untrusted LAN.
- Probe before publishing available, propagate sidecar/open failures into unavailable state, clear state on deconfigure, and remove the fallback phantom camera. Log one unavailable and one recovered transition.
- Monitor the Wyze child process, wait for authenticated readiness before configure succeeds, distinguish `starting/degraded/stopped`, restart with bounded backoff, and surface terminal failures.

### P1 — complete the camera/media contract

- Add a still-image/snapshot path with the same authorization and secret boundary. Decide whether recording and `play_stream` are product requirements; if yes, expose a brokered HLS/recording path rather than pretending native WebRTC alone supplies them.
- Implement candidate exchange/trickle ICE, client-driven close ownership, activity-based expiry/keepalive, and TURN/STUN configuration. Test LAN, NAT, relay, disconnect, browser refresh, and abandoned-session behavior.
- Honor `include_audio`. Probe audio tracks and add Opus/PCMU/PCMA normalization when needed. Publish tested codec/container/browser behavior and explicit CPU limits. Consider shared producer reuse so concurrent viewers do not create avoidable camera sessions.
- Turn refresh into a real source probe. Add reconnect state, bounded backoff/jitter, and stale thresholds. Emit non-secret session/probe/recovery counters.

### P2 — Wyze product completeness

- Build the missing end-user Wyze integration that owns authorization, reauthentication/API-key expiry, camera entity creation/removal, dynamic camera changes, and service handoff. Until then, describe this component only as infrastructure.
- Qualify exact upstream camera models/firmware from the pinned v2.10.3 support table rather than saying “cameras supported by docker-wyze-bridge.” Include known unsupported/partial models and cloud/P2P/LAN limitations ([upstream model table](https://github.com/mrlt8/docker-wyze-bridge/blob/v2.10.3/README.md#supported-cameras)).
- Decide which upstream functions are in scope: snapshots, substreams, audio controls, motion/offline signals, PTZ/accessories, and two-way audio. Expose only tested capabilities; do not infer support from upstream presence.
- Provide credential renewal and recovery UX consistent with Wyze's official expiry/rate-limit guidance.

### P3 — quality and release evidence

- Add a checked-in PiPhi quality checklist mapping every applicable IQS rule to code/test/docs evidence and giving explicit exemption reasons for HA-specific rules.
- Add public, required CI for all three packages: locked dependency install; lint/format/type checks; unit and contract tests; coverage threshold; container build; vulnerability/license scan; SBOM/provenance; upstream digest verification; and an integration test with the real pinned go2rtc binary.
- Add a gated hardware matrix for representative RTSP cameras and supported Wyze generations, with browser clients, audio, camera offline/online, cloud outage, credential expiry, process crash, packet loss, concurrent viewers, and long-running reconnect tests.
- Generate release docs/version examples from manifests and reconcile publication/rollout claims. Link immutable CI runs, attestations, and releases from the manifests.

## IQS tier assessment

This is a comparative assessment, not an HA certification. HA marks its go2rtc/stream components as internal integrations, while PiPhi distributes three separate runtime packages.

| Tier | Result | Evidence and blockers |
|---|---|---|
| Bronze | **Not demonstrated** | Positive: UI schema, open-source pinned upstreams, contract tests, maintainer metadata, and high-level docs. Blockers include no verified public CI/dependency publication evidence, no connection test before accepting RTSP/Wyze configuration, no duplicate-source prevention, incomplete install/removal/trigger/condition documentation, a no-op refresh action, and no checked-in quality checklist. The absent end-user Wyze integration means its config flow cannot be assessed. |
| Silver | **Not met** | No truthful unavailable/recovered entity behavior, no reauthentication flow, no reconnect transition logging, no demonstrated >95% per-module coverage, and incomplete unload/reload evidence across Core plus both services. |
| Gold | **Not met** | Diagnostics are present but sparse; no discovery/dynamic/stale device lifecycle, translated errors/entities, repair issues, complete supported-device/known-limitations/troubleshooting docs, or verified reconfiguration UX. |
| Platinum | **Not assessed / not eligible** | Async code is used in much of the bundle, but strict typing evidence and web-session injection equivalence are absent, and lower tiers are not met. |

The manifests' current `quality_tier: unrated` is therefore accurate and should remain so.

## Safety invariants

These invariants should become executable cross-package tests and deployment policy:

1. A browser/widget can receive SDP/media metadata but never a camera source URL, Wyze credential, API key, stream password, or go2rtc administration capability.
2. Every endpoint that accepts account/source secrets or returns a credential-bearing descriptor fails closed in production when service identity is missing or wrong.
3. go2rtc API and RTSP control listeners remain loopback-only; only encrypted WebRTC transport is externally reachable from the sidecar. The Wyze RTSP listener is reachable only by explicitly authorized PiPhi consumers.
4. Source URLs and SDP never appear in logs, exceptions, events, health, diagnostics, state, traces, crash reports, or persistence. IDs/hostnames are redacted where user-exported diagnostics could identify a home.
5. Deconfigure, session close/expiry, process crash, and container shutdown remove upstream streams, cancel tasks, clear in-memory credentials, and revoke generated stream credentials.
6. Availability means a recent successful source/bridge check, not merely that configuration exists. A stale or failed source becomes unavailable within a documented bound and recovers automatically with bounded backoff.
7. Session capacity, SDP size, source URL length/scheme, probe output, process time, transcode CPU/memory, and reconnect rate remain bounded under hostile or broken inputs.
8. Codec claims are based on negotiated end-to-end playback. Unsupported audio/video fails clearly or uses a tested fallback; it never silently reports a healthy stream.
9. Upstream images are version-and-digest pinned, licenses/notices are preserved, and releases are traceable to required CI, SBOM, provenance, vulnerability review, and hardware qualification.
10. Wyze account use follows official key/token lifetime and rate-limit guidance; no automatic retry loop repeatedly calls login or locks out the account.
