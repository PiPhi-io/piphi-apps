# PiPhi Zigbee delivery-stack quality comparison

**Rebaseline date:** 2026-11-17

**PiPhi revision audited:** [`44f88d9`](https://github.com/PiPhi-io/piphi-apps/tree/44f88d9f1ae1e980d85d05ebf9163532bef137b7)

**Scope:** `apps/integrations/piphi-network-zigbee` source candidate 0.1.13 and `apps/services/piphi-network-zigbee2mqtt` source candidate 0.1.27, assessed as one delivery stack.

> **Post-audit remediation status:** The P0 findings recorded by the 0.1.13/0.1.25 rebaseline have been closed in the 0.1.13/0.1.27 release candidates. MQTT delivery now uses a bounded ordered journal with monotonic cursors and explicit gap reporting; startup and runtime availability distinguish broker, bridge, coordinator, and device evidence; recoverable backups require fenced workload state, essential files, and fresh coordinator material for governed families; claims use stable runtime identity, leases, heartbeat renewal, fencing generations, and authenticated stale repair; destructive network changes require recoverable backup, warning, and confirmation; and migration rejects free-form/cross-family evidence in favor of governed same-family records. The historical gap table below is retained as the rationale for that work; the remediation statements in this note take precedence.

**External baseline:** Home Assistant Core [`4adb2b9`](https://github.com/home-assistant/core/tree/4adb2b903c1f03354c6fa8ae45dc2b80826d9e51/homeassistant/components/zha), Home Assistant documentation [`f178f5f`](https://github.com/home-assistant/home-assistant.io/blob/f178f5fdb3bfa292cd4fbefdaf95162dbd37833c/source/_integrations/zha.markdown), and Zigbee2MQTT documentation [`b06b2f0`](https://github.com/Koenkk/zigbee2mqtt.io/tree/b06b2f02549d2d4aca907018dc897fd084707810). PiPhi pins Zigbee2MQTT 2.14.3 by container digest ([PiPhi setting](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/settings.py#L13-L16), [upstream tag](https://github.com/Koenkk/zigbee2mqtt/tree/3c841fdfd66c92239921ef84fde8f039c64e1662)).

## Executive conclusion

The previous comparison was **stale as a current assessment**. Its main table and work list still described the 0.1.10/0.1.18 implementation even though appended notes recorded remediation through sidecar 0.1.25. This rebaseline replaces those contradictory sections.

The combined stack now has a credible, security-conscious **managed Zigbee2MQTT bridge foundation**. Since the original audit it has added mandatory production-sidecar authentication, verified `mqtts://`, end-to-end interview eligibility filtering, a managed MQTT namespace, non-root/no-device/no-Docker-socket sidecar deployment, stable coordinator claims and in-use checks, validated network identity, private checksummed backups, authenticated encrypted export/import, stopped-workload evidence, restore rollback, and a guided migration API. Those are substantial remediations, not documentation-only claims ([authorization](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/authorization.py), [container manifest](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/manifest.json#L60-L90), [backup implementation](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/network_backup.py), [migration routes](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/routes/bridge.py#L151-L305)).

It is still **not comparable to ZHA as a general-purpose Zigbee product**. ZHA directly implements an endpoint-aware Zigbee application model and currently documents 18 Home Assistant device domains, groups, binding, install-code commissioning, OTA updates, network information/channel changes, automatic/manual backups, and guided migration ([ZHA docs](https://github.com/home-assistant/home-assistant.io/blob/f178f5fdb3bfa292cd4fbefdaf95162dbd37833c/source/_integrations/zha.markdown)). PiPhi currently turns each physical Zigbee device into one generic entity, recognizes a small fixed property vocabulary, and publishes only refresh, on/off/toggle, brightness, and color-temperature requests ([normalizer](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/integrations/piphi-network-zigbee/src/piphi_network_zigbee/zigbee_devices.py#L6-L37), [commands](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/integrations/piphi-network-zigbee/src/piphi_network_zigbee/mqtt_runtime.py#L238-L250)).

**Release recommendation:**

- Release integration 0.1.13 with sidecar 0.1.27 as one constrained managed-helper stack after exact-image qualification.
- Do **not** promote integration candidate 0.1.13 as a general-purpose, HA-equivalent, safety-monitoring, or broadly production-ready Zigbee integration.
- A truthful near-term claim is: **“PiPhi-managed Zigbee2MQTT setup and recovery for a qualified coordinator, plus a tested basic MQTT state/control adapter for a constrained set of exposes.”**
- Keep marketplace quality `unrated`, publication `draft`, qualification `unverified`, and rollout `0`; the software P0 items are closed, but this remains a constrained preview rather than a ZHA-parity or broad hardware-support claim.

## Architecture and comparison model

ZHA and PiPhi do not share an implementation architecture. ZHA owns one coordinator directly through `zha`/`zigpy`; PiPhi supervises an upstream Zigbee2MQTT workload and translates part of its MQTT contract. Zigbee2MQTT is therefore the authority for PiPhi's wire behavior, while ZHA is an analogical benchmark for onboarding, identity, entity quality, recovery, diagnostics, and user safety. Both owning projects state that one coordinator cannot be shared with another application ([ZHA limitation](https://github.com/home-assistant/home-assistant.io/blob/f178f5fdb3bfa292cd4fbefdaf95162dbd37833c/source/_integrations/zha.markdown#troubleshooting), [Zigbee2MQTT limitation](https://github.com/Koenkk/zigbee2mqtt.io/blob/b06b2f02549d2d4aca907018dc897fd084707810/docs/guide/faq/README.md#general-limitations-that-apply-to-all-zigbee-implementations)).

This document uses Home Assistant's quality dimensions only as review prompts. PiPhi is not a Home Assistant Core integration, and ZHA has no `quality_scale.yaml` at the observed Core revision. No official Home Assistant tier is claimed.

## Supported functionality verified in source

### Setup, ownership, and transport

- Linux Core-managed-helper deployment is non-root and the sidecar receives one RW data volume, no coordinator device, no Docker socket, and no privileged mode. Docker lifecycle calls return `managed_by_core`; the sidecar does not execute Docker commands ([Dockerfile](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/Dockerfile#L24-L31), [supervisor](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/supervisor.py#L71-L82)). Windows/macOS metadata still specifies a native PM2-managed Zigbee2MQTT process.
- Production requests to sensitive sidecar paths fail closed without a bearer token; `/v1/*` is covered by middleware. This is service-level authentication, not fine-grained per-operation authorization ([middleware](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/app.py#L14-L42)).
- Core-managed stop evidence is operation-bound, coordinator-bound, HMAC-authenticated, valid for at most 30 seconds, and one-time through a SQLite nonce ledger ([evidence](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/stopped_coordinator_evidence.py#L15-L101)).
- Local serial ownership checks inspect Linux `/proc` descriptors or use an exclusive serial open. Network coordinators get reachability only; remote exclusivity cannot be proven ([probe](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/coordinator_probe.py#L29-L110)).
- The managed MQTT gateway owns one broker connection, scopes reads/writes to the assigned base topic, rejects wildcards/out-of-namespace topics, bounds payloads to 64 KiB, publishes with QoS 1, and performs default certificate/hostname verification for `mqtts://` ([gateway](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/mqtt_gateway.py), [TLS](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/zigbee2mqtt_mqtt.py)).

### Commissioning, inventory, and device behavior

- Serial discovery prefers stable Linux links and hints `zstack`, `ember`, `deconz`, `zigate`, or `zboss`; this is detection, not hardware qualification. The UI still lists ZiGate and ZBOSS without reflecting Zigbee2MQTT's “not maintained” and “experimental” labels ([PiPhi manifest](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/manifest.json#L139-L149), [upstream adapter status](https://github.com/Koenkk/zigbee2mqtt.io/blob/b06b2f02549d2d4aca907018dc897fd084707810/docs/guide/adapters/README.md)).
- Configuration covers MQTT endpoint/credentials/base topic, serial port/adapter/baud/LED, frontend, availability, channel, PAN ID, extended PAN ID, and 16-byte network key. Form-new requires confirmation; `GENERATE` is restricted to form-new; and channel/PAN/key changes require a recoverable backup, explicit warning acknowledgement, confirmation, and operation-bound stopped-workload evidence.
- Retained inventory, transaction-correlated time-bounded permit-join, and manual raw network maps follow Zigbee2MQTT's documented MQTT API. Discovery now rejects coordinators, unsupported devices, and failed/in-progress interviews on both the sidecar and integration sides ([device model](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/bridge_models.py#L441-L474), [integration filter](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/integrations/piphi-network-zigbee/src/piphi_network_zigbee/zigbee_devices.py#L170-L183), [upstream API](https://github.com/Koenkk/zigbee2mqtt.io/blob/b06b2f02549d2d4aca907018dc897fd084707810/docs/guide/usage/mqtt_topics_and_messages.md)).
- IEEE address is the preferred stable PiPhi identity; friendly name remains routing metadata/fallback. Expose access bits gate writable controls. State supports common environmental, power, presence/contact, and smoke/CO/leak properties; commands support refresh, state, brightness, and color temperature.

### Backup, restore, and migration

- PiPhi archives bounded regular files from the Zigbee2MQTT data directory, excludes control-plane state and backup recursion, records sidecar/Zigbee2MQTT/adapter metadata, uses SHA-256, private permissions, safe extraction, pre-restore rollback, and AES-256-GCM exports with a scrypt-derived key ([backup source](https://github.com/PiPhi-io/piphi-apps/blob/44f88d9f1ae1e980d85d05ebf9163532bef137b7/apps/services/piphi-network-zigbee2mqtt/src/piphi_network_zigbee2mqtt/network_backup.py)).
- Restore requires explicit confirmation, a stopped local coordinator or fresh Core evidence, a claim, checksum and adapter-family compatibility. Migration uses plan/apply IDs, rechecks target availability, takes rollback material, restores, retargets config, and rolls back data on post-restore failure.
- Qualification notes committed on 2026-11-16 record one physical Sonoff ZBDongle-P (`10c4:ea60`, ZStack firmware `20210708`) passing stable discovery, fenced start/restart, unplug/replug recovery, encrypted export/import, stopped restore, and same-physical/same-family migration against released Core and sidecar 0.1.25 artifacts. This is useful evidence for that exact path, not a hardware matrix or a second-radio migration ([qualification commit](https://github.com/PiPhi-io/piphi-apps/commit/f11eb79)).

## Security, privacy, and lifecycle findings

### Closed or materially remediated since the original audit

1. Sensitive sidecar routes are no longer unauthenticated in production.
2. `mqtts://` no longer silently means plaintext on port 8883.
3. Coordinator/unsupported/incomplete interview records no longer pass normal discovery.
4. Linux sidecar no longer runs privileged/root or owns the Docker socket/coordinator device.
5. Caller-controlled supervisor image/name/path/environment options are allowlisted.
6. Network key/PAN shape validation, redacted serialization, private writes, explicit form-new semantics, and backup gates now exist.
7. Backup integrity, encrypted portable export/import, stopped restore, rollback, and guided migration now exist.
8. Core-managed operations use short-lived operation-specific evidence rather than trusting an assertion that a coordinator is stopped.

### Still open after the 0.1.13/0.1.27 remediation

1. **Remote coordinators:** do not treat TCP reachability as exclusivity. Require an owning helper/lease protocol or explicitly label remote ownership unverified.
2. **Commissioning authorization:** permit-join should have operation-level authorization, audit, caller-loss cleanup, explicit close, progress, retry, and install-code support.
3. **Identity reconciliation:** consume inventory/events and update friendly-name topics without changing IEEE/endpoint identity or duplicating devices.
4. **Private diagnostics:** define event/telemetry retention, minimize raw payload/name/IEEE export, and add redaction regression tests plus useful radio/bridge evidence.

## Prioritized work

### P0 — closed in the 0.1.13/0.1.27 candidates

1. State/action/safety delivery is ordered and loss-detectable through the bounded journal and explicit overflow gaps. This still does not make the product alarm-grade.
2. Startup is unknown; broker/bridge/coordinator/device evidence and bridge-loss propagation are modeled separately.
3. Backup evidence requires fenced workload state, essential files, fresh coordinator material where governed, and post-restore verification hooks; destructive channel/network changes require warning and confirmation.
4. Coordinator ownership uses leases, heartbeat renewal, fencing generations, compare-and-swap stale repair, and authenticated repair confirmation.
5. Migration is restricted to governed same-family compatibility records; caller-supplied free-form and cross-family evidence is rejected.

### P1 — reliable supported product

1. Build endpoint-aware, schema-driven entities and commands for a deliberately qualified first set of domains. Preserve repeated endpoint properties, enum/range/step/unit/category metadata, and unknown exposes.
2. Subscribe to bridge inventory/state/info/health/event; reconcile add/remove/rename/interview and expose repair guidance.
3. Correlate commands to an upstream response and device state convergence; distinguish broker acceptance, bridge rejection, timeout, and device outcome.
4. Add install-code commissioning, explicit permit-close/audit, remove/re-interview/reconfigure, and hardware-status warnings aligned with upstream.
5. Add downloadable privacy-safe diagnostics and a versioned hardware matrix covering exact PiPhi/Core/Z2M artifacts, coordinator model/firmware, OS/runtime, restore, migration, and outage recovery.
6. Pin the integration Docker base image as the sidecar already does; add Ruff, dependency audit, and a coverage threshold to integration CI.

### P2 — breadth and quality

1. Add groups, scenes, binding, reporting, device options, topology guidance, channel workflow, and guarded OTA.
2. Add typed support for color lights, covers, fans, climate, locks, valves, sirens, numbers/selects, updates, and configuration/diagnostic exposes only as each mapping is tested.
3. Add accessible onboarding/removal/recovery documentation, translated errors, stale-device cleanup, and bounded soak/disconnect tests.

## Test and release evidence

- The audited tree contains **48 integration test functions** and **61 sidecar test functions**; parameterization makes function counts lower than collected case counts.
- The committed 2026-11-16 qualification record reports **210 integration cases passed**, **61 sidecar cases passed**, sidecar validator/Ruff/dependency audit/container build passed, **35 focused Core managed-runtime/contract cases passed**, and the single Sonoff hardware exercise described above.
- After P0 remediation, isolated PDM environments reproduced **212 passing integration cases** and **85 passing sidecar cases**. Both scaffold validators and sidecar Ruff also passed.
- Test inspection found meaningful negative cases for authorization, TLS, topic namespace, coordinator claims/probes, one-time stop evidence, interview filtering, backup tamper/wrong-passphrase/safe extraction, restore compatibility/rollback, and migration confirmation/plan matching.
- Most tests are mocked/in-process. The recorded physical evidence covers one USB coordinator and same-physical same-family migration only. It does not prove Windows/macOS PM2, network coordinators, a second physical target, other adapter families, RF scale, device-domain breadth, event bursts, broker outage recovery, or OTA.
- Integration 0.1.13 and sidecar 0.1.27 are source candidates pending source merge and exact-image release qualification; the previously published tags remain integration 0.1.11 and sidecar 0.1.25.
