# Home Assistant AI/LLM quality comparison

**Research cutoff:** 2026-11-16

**PiPhi revision audited:** [`e3eb2d3`](https://github.com/PiPhi-io/piphi-apps/tree/e3eb2d3084645ab2cf4f80e925368b28f6fdb27e/apps/services/piphi-network-llm-vision)
**Comparison baseline:** Home Assistant Core [`7682317`](https://github.com/home-assistant/core/tree/76823177f8d296dbbf017fe59627757b695e71d5) and developer documentation [`50b5188`](https://github.com/home-assistant/developers.home-assistant/tree/50b518898989b67bb76b69827f227aa6f0acd32a)

## Executive conclusion

`piphi-network-llm-vision` is correctly classified as a **platform service/sidecar**, not a Home Assistant entity integration. At the audited revision it is also **not an LLM vision implementation**. It is a generated FastAPI runtime scaffold that stores configuration in memory, reports a synthetic connected state, accepts a no-op `refresh`, and exposes sample event/telemetry routes. Its own capability catalog accurately marks analysis jobs, provider routing, retention, memory, and backpressure as planned, while the README and manifest describe a future safe boundary.

The honest supported slice is therefore: **PiPhi runtime contract plumbing only**. There is no image or video ingress, provider SDK/client, model discovery, prompt construction, AI Task adapter, conversation/ChatLog adapter, HA LLM tool API, structured-output execution, provider fallback, moderation, or usage/cost accounting. Passing scaffold tests establish internal route/catalog consistency; they do not establish AI quality, privacy, security, provider compatibility, or operational readiness.

This narrowness currently avoids direct media exfiltration, prompt injection into tools, arbitrary URL/file fetches, and provider spend. It must not be mistaken for implemented safeguards. In particular, configuration accepts `api_key` and stores the full model dump in the registry, command arguments are copied into local events, service-owned inbound authorization is not visible, the image is neither built in CI nor pinned by digest, and the published/runtime image metadata conflicts between Docker Hub and GHCR. **Do not expose this service to real camera media or provider credentials until the P0 items below are complete.**

Home Assistant's first-party baseline is materially deeper, but it should not be misread as a provider-count contest. HA supplies a common AI Task contract with permission-checked media-source attachments and schemas, a conversation `ChatLog`, per-request authorized LLM APIs/tools, conservative tool annotations, bounded tool loops, and mature provider-specific adapters. PiPhi can support fewer providers and still be high quality; it cannot claim quality merely by accepting an OpenAI-compatible URL or listing many planned providers.

## Scope and method

The audit inspected all reachable package source, tests, manifests, examples, privacy/release docs, tracked SQLite state, monorepo CI/release routing, and path history. It compared those artifacts with first-party HA AI Task, conversation, LLM API, and representative first-party provider implementations, plus owning-provider privacy/API documentation. HA's Integration Quality Scale (IQS) is used as an **inspiration for a platform-service assessment**, not as a claim that this sidecar is or can be assigned an HA IQS tier.

## Honest supported slice

### Supported now

- FastAPI process and PiPhi runtime routes (`/health`, `/diagnostics`, `/config`, `/state`, `/events`, `/telemetry/*`, `/command`).
- In-memory config registry and synthetic `connected: true` state after any accepted config.
- One `refresh` action that records and returns the submitted command; it does not contact a model or service.
- Local runtime events, outbound example telemetry scheduling, config synchronization hooks, and SQLite automation idempotency supplied by `piphi-runtime-kit-python`.
- Fail-closed command allow-list: catalog tests verify obvious unsafe/unimplemented commands such as `analyze_arbitrary_url` are rejected.
- Container process packaging and a Core-assigned `PORT` contract.

### Not supported now

- HA `ai_task.generate_data`, evaluation, image generation, attachments, preferred entities, or selector/probatio structured schemas.
- HA conversation entities, conversation IDs/history semantics, streaming, or `ChatLog`.
- HA LLM API selection, `LLMContext`, permission propagation, exposed-entity controls, tools, tool annotations, or tool-call result semantics.
- Any image/video/frame ingest, MIME sniffing, byte/pixel/frame/duration limits, camera/media-source resolution, temporary-file lifecycle, or broker attestation.
- Any provider/model client, allow-list, capability negotiation, endpoint TLS policy, model pinning, local-provider implementation, or cloud-provider implementation.
- Prompt assembly, role separation, prompt-injection handling, output parsing/validation, confidence calibration, moderation, or human review gates.
- Queueing, cancellation, concurrency limits, deadlines, retry/backoff, rate-limit handling, circuit breaking, fallback, cost/token budgets, or usage telemetry.
- Analysis-result retention/deletion, media deletion guarantees, per-user consent, subject redaction, or provider-specific data-flow disclosure.

## Privacy and security invariants

These are release-blocking invariants, not optional documentation goals.

1. **Explicit purpose-bound consent:** every job identifies requesting principal, installation/config, source camera/media, purpose, and consent grant. No continuous surveillance or implicit enrollment.
2. **Brokered bytes only:** accept opaque broker handles with single-use/short TTL authorization; never arbitrary URLs or filesystem paths. Resolve only through a broker client with destination allow-listing and DNS/IP revalidation.
3. **Verify content, not names:** enforce allow-listed MIME after magic-byte decode; byte, pixel, dimension, frame, duration, decompression, and aggregate request limits; reject polyglots/animation when unsupported.
4. **Least data:** sample the minimum frames, downscale/redact before cloud egress where configured, and never send unrelated state, camera names, household identities, location, or history by default.
5. **Destination transparency:** each job records and exposes the exact provider, endpoint class (local/LAN/cloud), region where known, model/snapshot, and enabled provider features. No silent local-to-cloud or provider fallback.
6. **Secrets by reference:** credentials live in the host secret store and are injected only into the selected outbound client. Never put secrets in config models, registry/state/events/telemetry/prompts/errors/diagnostics or idempotency rows. Automated secret-canary tests cover every output surface.
7. **Network containment:** default-deny egress except resolved provider/broker destinations; require HTTPS and certificate validation for cloud; explicitly label and constrain LAN exceptions; block loopback, link-local, metadata, multicast, private ranges, redirects, and DNS rebinding unless the selected local provider policy requires a narrowly configured address.
8. **Prompt/tool separation:** system policy, user instruction, media-derived text, memory, and tool output remain distinct. Treat OCR/captions as hostile data. Vision analysis cannot invoke tools or device actions; any future action needs separate HA authorization and human/policy approval.
9. **Typed output:** use provider-native strict schemas when available, validate locally against the requested schema, bound strings/arrays/numbers, reject extra fields, refusals and truncation, and never convert confidence-like text into a safety decision.
10. **Bounded execution:** per-job deadline, cancellation propagation, max provider/tool iterations, max output tokens, queue job/byte caps, per-config concurrency/fairness, bounded idempotent retries with jitter and `Retry-After`, and overload rejection before reading media.
11. **Cost safety:** preflight worst-case media/token estimate; per-job and rolling per-config budgets; output caps; usage reconciliation; no retries/fallback after budget exhaustion; user-visible estimate and actual provider usage where available.
12. **Retention is executable:** default no raw-media persistence; delete temp bytes immediately after terminal state; explicit short TTL for results/events/idempotency; atomic purge on deconfigure; provider feature-specific disclosure and deletion behavior; auditable deletion receipts without retaining content.
13. **Safe observability:** structured, low-cardinality logs and metrics use random job IDs and coarse error classes. No prompts, media, provider bodies, tool args/results, signed URLs, household identifiers, or credentials. Debug mode cannot weaken this invariant.
14. **Moderation and sensitive inference:** define supported use cases and forbidden outputs. Do not perform face recognition, unknown-person identification, protected-trait inference, medical/legal/safety determinations, or child profiling. Provider moderation is additive and fail-closed where the declared use case requires it.
15. **Lifecycle and provenance:** validate provider capability at setup; distinguish auth/quota/rate/transient/permanent failure; stop admission before shutdown, cancel/drain safely, clean temporary data, recover only metadata needed for idempotency, and ship a scanned, signed, digest-pinned multi-arch image with SBOM/provenance.

## Prioritized work

### P0 — before real media, credentials, or public exposure

1. **Choose and specify one vertical slice:** brokered still image → one explicitly configured provider/model → text plus optional HA-compatible structured result. State that conversation, video/stream, memory, timeline, tools/device control, biometrics, and fallback are out of scope.
2. **Define a typed job API and threat model:** principal/config/purpose/consent, broker handle, instruction, schema, deadline, idempotency key, provider destination, limits, terminal states, and typed errors. Authenticate and authorize every non-health route.
3. **Implement safe broker ingress:** no URL/path parameters; one-shot media authorization; streaming byte limit; MIME/magic/pixel validation; bounded decode; temp storage with restrictive permissions and guaranteed cleanup. Add malicious-media and SSRF regression tests.
4. **Fix secret handling:** remove `api_key` from runtime config/state models; accept a secret reference; redact all request/event/state/diagnostic/error surfaces; prevent arbitrary command args from entering events; add canary tests.
5. **Implement one provider adapter with explicit capabilities:** immutable model/snapshot where possible, TLS policy, connect/read/overall deadlines, output limit, strict schema support matrix, typed error mapping, usage capture, and no fallback. Mock it deterministically in tests.
6. **Enforce resource/cost controls:** queue bytes/jobs, per-config concurrency, cancellation, deadline, frame/image/token/output caps, preflight cost estimate, daily budget, bounded retry policy, rate-limit handling, and overload behavior.
7. **Implement retention/consent UX and deletion:** exact local/provider data flow, provider feature caveats, default TTLs, purge/deconfigure path, and local-vs-cloud label. Require a fresh explicit opt-in before cloud media transfer.
8. **Harden delivery:** switch to full CI, build/test the container on amd64/arm64, run coverage/security/dependency/image scans, generate SBOM/provenance, sign and pin image digest, and reconcile GHCR/Docker Hub/version/release docs.
