## Executive conclusion

`piphi-mqtt-broker` is an honest but narrow Mosquitto wrapper: it can provide password-authenticated or explicitly anonymous MQTT over plain TCP, supports the MQTT versions implemented by its packaged Mosquitto, persists retained messages and durable-session state, and restarts under the platform policy. Anonymous access is off by default and startup fails when no credential is supplied. Those are useful foundations.

It is **not production-ready as shared, multi-tenant platform infrastructure**. The single generated user has no ACL, `MQTT_TOPIC_PREFIX` is never applied, and any authenticated client can publish and subscribe across the broker. The only listener binds to `0.0.0.0` and has no TLS, so MQTT credentials and payloads are cleartext on every network path that can reach it. There are no broker-level connection, session, message-byte, queue-byte, or memory quotas; no health check; no managed credential rotation/revocation; no backup/restore procedure; no bridge policy; and no runtime or failure-path test in CI. These are boundary and lifecycle gaps, not missing Home Assistant entities.

The current supported slice is suitable only for a **single trust domain on a separately protected network**, with one static credential, modest traffic, externally managed volume backup, and manual Home Assistant broker configuration. It should not be described as isolated multi-tenant messaging, internet/LAN-safe MQTT, a highly available broker, or a drop-in equivalent of the official Home Assistant Mosquitto app.

The comparison baseline is intentionally demanding:

- The current first-party Home Assistant MQTT integration is a Platinum, local-push **service** integration, not a broker ([immutable manifest](https://github.com/home-assistant/core/blob/00783549b0080feaa9af81a29d5ad839a8f0bc96/homeassistant/components/mqtt/manifest.json#L1-L16)). Its owning documentation says the broker must support MQTT 5, supports TCP/WebSockets, TLS validation and client certificates, and relies on retained discovery/state plus birth/LWT behavior ([protocol and transport](https://github.com/home-assistant/home-assistant.io/blob/c61ecf719cbe63ab1df41d57015e47f91394ad3a/source/_integrations/mqtt.markdown#L99-L128), [birth/LWT](https://github.com/home-assistant/home-assistant.io/blob/c61ecf719cbe63ab1df41d57015e47f91394ad3a/source/_integrations/mqtt.markdown#L153-L171)).
- The official Home Assistant Mosquitto app 7.1.3 supplies Home Assistant-managed and local users, four MQTT/MQTT-over-WebSocket listeners, optional TLS/client certificates, persistent data, customization, a TCP health check, and a larger queue allowance ([immutable config](https://github.com/home-assistant/app-mosquitto/blob/d08790bb7a9f6b0d477f8ec39df9a87f396dfe67/mosquitto/config.yaml#L1-L52), [broker template](https://github.com/home-assistant/app-mosquitto/blob/d08790bb7a9f6b0d477f8ec39df9a87f396dfe67/mosquitto/rootfs/usr/share/tempio/mosquitto.gtpl#L1-L91), [health check](https://github.com/home-assistant/app-mosquitto/blob/d08790bb7a9f6b0d477f8ec39df9a87f396dfe67/mosquitto/Dockerfile#L84-L85)). It is itself not a multi-tenant policy model by default: its documentation recommends individual users and custom ACLs when topic restriction is required ([immutable app documentation](https://github.com/home-assistant/app-mosquitto/blob/d08790bb7a9f6b0d477f8ec39df9a87f396dfe67/mosquitto/DOCS.md#L160-L189)).

## Honest supported slice

### Supported and verified

- One standard TCP MQTT listener, defaulting to all IPv4 interfaces on port 1883 ([defaults](../src/config.ts#L15-L25), [rendering](../src/mosquitto.ts#L15-L26)).
- MQTT 5 connection and retained publish/subscribe against the built image. Mosquitto itself supports MQTT 5.0, 3.1.1, and 3.1 ([primary documentation](https://github.com/eclipse-mosquitto/mosquitto/blob/a7f3f4c362713d6e35ed75745f38ae8aaac78443/man/mosquitto.8.xml#L150-L175)).
- Anonymous access denied by default; startup rejects missing or half-configured credentials ([validation](../src/config.ts#L75-L104)). Anonymous mode is an explicit opt-in.
- A hashed Mosquitto password file for exactly one environment-provided user, with mode `0640` when the `mosquitto` account exists ([entrypoint](../docker/entrypoint.sh#L4-L17)).
- Built-in persistence enabled by default at `/mosquitto/data/`, with config/data/log host mounts and `unless-stopped` restart policy ([manifest](../src/manifest.json#L11-L41)). Mosquitto persistence includes subscriptions, sessions, and messages and reloads `mosquitto.db` after restart ([primary documentation](https://github.com/eclipse-mosquitto/mosquitto/blob/a7f3f4c362713d6e35ed75745f38ae8aaac78443/man/mosquitto.conf.5.xml#L1007-L1038)).
- OCI publication for `linux/amd64` and `linux/arm64`, with release SBOM and build-provenance generation ([package metadata](../piphi-app.json#L24-L51), [release workflow](../../../../.github/workflows/release-app.yml#L138-L157)).

### Not supported or not qualified

- TLS server listeners, mTLS, WebSockets, Unix sockets, listener-specific policy, or secure bridge transport.
- Per-client credentials, roles, ACLs, topic-prefix enforcement, tenant isolation, credential revocation, online rotation, or short-lived credentials.
- Managed bridges. There is no `include_dir` or bridge schema, and generated `mosquitto.conf` is replaced at every start.
- Capacity policy: no explicit maximum clients/sessions, message or packet size, queued bytes, inflight bytes, memory, keepalive, or stale durable-session expiry.
- Health/readiness, HA/failover, replication, fencing, drain, corruption recovery, or automated restore.
- Home Assistant Supervisor discovery/credential handoff. Home Assistant can use this broker only by configuring it as an ordinary external broker. By contrast, the official path generates and keeps integration credentials secret and updates them after app reinstallation ([first-party MQTT documentation](https://github.com/home-assistant/home-assistant.io/blob/c61ecf719cbe63ab1df41d57015e47f91394ad3a/source/_integrations/mqtt.markdown#L59-L68)).

## HA IQS-inspired platform-quality assessment

The HA IQS is designed for Core integrations, so entity rules, device-info rules, config-entry unload, translations, and service actions are inapplicable. The following adapts its user-journey, reliability, diagnostics, security, documentation, and test intent to a broker platform service.

| Platform-quality dimension | Result | Rationale |
|---|---|---|
| Correct service boundary | **Meets** | Correctly modeled as a shared platform service rather than fake MQTT entities. |
| Install/configure/reconfigure journey | **Partial** | Small schema and fail-fast credentials, but no HA discovery handoff, TLS, validation constraints, secret references, or safe rotation workflow. |
| Secure defaults | **Partial** | Anonymous-off is good; all-interface cleartext, one global principal, and no resource limits are not. |
| Authentication and credential lifecycle | **Does not meet** | One environment secret, recreated file, no revocation/rotation/reload/forced disconnect. |
| Authorization and tenant isolation | **Does not meet** | No ACL and unused prefix; authenticated clients share the entire namespace. |
| Data integrity and restart behavior | **Partial** | Persistence and controlled restart work; no crash, disk-full, corruption, upgrade, or restore evidence. |
| Availability and recovery | **Does not meet** | No health/readiness, HA, failover, recovery runbook, or tested backup. |
| Capacity and abuse controls | **Does not meet** | Broker resource policy is almost entirely upstream defaults, several unlimited. |
| Observability and privacy | **Does not meet** | Logs only, no metrics/diagnostics/redaction contract; `$SYS` access is not isolated. |
| Protocol interoperability | **Meets narrow slice** | MQTT 5 and retained persistence verified; MQTT TCP only. |
| Documentation and known limitations | **Partial** | README describes the wrapper and future TLS/health, but not the trust boundary, cleartext risk, unrestricted authorization, persistence semantics, recovery, or capacity envelope. |
| Automated tests | **Does not meet** | Unit/metadata tests pass but no broker/container integration suite. |

**Overall:** below a production platform baseline. Do not map this to a Bronze/Silver/Gold/Platinum HA IQS tier; the meaningful release gate is completion of the P0 security invariants and broker-level qualification below.

## Required security invariants

These should be executable release and deployment assertions, not documentation-only promises.

1. **Default deny:** no anonymous connection in production; absence or invalidity of auth policy prevents readiness.
2. **Unique workload identity:** each integration, bridge, operator, and Home Assistant client has a distinct revocable principal. Shared static credentials are prohibited.
3. **Least-privilege topics:** every principal has explicit publish, receive, subscribe, and unsubscribe rights; no application principal receives `#`, `$SYS/#`, or `$CONTROL/#` by default.
4. **Enforced tenant boundary:** the configured tenant/topic prefix is enforced by ACL, role, or listener mount point. Merely exporting `MQTT_TOPIC_PREFIX` is insufficient.
5. **Confidential transport:** every path crossing a container/host or trust boundary uses verified TLS (or an equivalently documented, enforced encrypted overlay). Plain 1883 is bound only to an explicitly private interface and is opt-in.
6. **Secret hygiene:** raw passwords never appear in image layers, generated config, process arguments, normal logs, diagnostic bundles, or general environment inspection. Use platform secret references/files and constant-time supported authentication.
7. **Safe credential change:** add/rotate/revoke is atomic, reloadable, audited, and tested. Rotation has overlap where needed; revocation defines whether existing sessions are forcibly disconnected.
8. **Bounded resource use:** connections, total sessions, inflight/queued messages and bytes, packet/payload size, memory, stale sessions, persistence growth, and container CPU/memory/disk are bounded and observable.
9. **Persistence confidentiality and integrity:** `mosquitto.db`, ACL/auth state, TLS keys, and backups are access-controlled and encrypted where the platform requires; restore cannot silently combine stale authorization with current tenants.
10. **Fail closed on malformed config:** all rendered values are typed/allowlisted, newline-free, and path-confined; config is syntax-checked before replacing the last known-good file.
11. **Authenticated readiness:** readiness proves a real MQTT 5 CONNECT plus publish/subscribe round trip using a health-only principal and verifies persistence storage is writable; liveness is separately process/socket based.
12. **No silent degradation:** queue drops, auth failures, disk pressure, persistence failures, bridge loops/outages, listener failures, and repeated restarts produce bounded logs, metrics, and actionable health state without payload/secret disclosure.
13. **Recoverability:** backup is quiesced or forced after a persistence flush, includes auth/ACL/TLS/config state, records broker/schema version, and is restored in an automated test before release.
14. **Qualified artifact identity:** deployment resolves an immutable image digest whose exact amd64/arm64 manifests passed protocol/security smoke tests and has verified SBOM/provenance and vulnerability policy results.

## Prioritized work

### P0 — block shared production use

1. **Implement managed identity and authorization.** Replace the one-user `-c` flow with Mosquitto dynamic security or managed password/ACL plugins. Generate one principal per workload, default-deny all topic operations, reserve admin/health roles, enforce tenant prefixes, protect `$SYS`/`$CONTROL`, and test cross-tenant denial including retained messages and existing subscriptions.
2. **Define and enforce the network/TLS boundary.** Add server TLS and optional mTLS, certificate/key/CA secret mounts, hostname-validating clients, rotation via SIGHUP, and a production policy that disables plain listeners. Until then bind only to a platform-private interface and explicitly document that the service is unusable on an untrusted LAN.
3. **Set abuse-resistant limits.** Establish workload-derived values for clients/sessions, connection rate at the network layer, packet/payload size, inflight/queued messages and bytes, stale-session expiry, memory, CPU, persistence disk and log rate. Alert before hard limits and exercise overload/drop behavior.
4. **Add a real health contract and resolve port publication.** Separate liveness/readiness/startup checks; readiness must authenticate and round-trip MQTT 5. Add an orchestration test proving `PORT`, container port mapping, service discovery, and exported `MQTT_PORT` all resolve to the same reachable listener.

### P1 — production reliability and release gate

1. **Build credential lifecycle APIs/workflows:** add, rotate, revoke, reload, disconnect, expiry, audit, and recovery; pass secrets by protected files rather than environment/process argv.
2. **Create backup/restore and upgrade contracts:** force persistence flush or clean stop, snapshot all coupled state, encrypt and version backups, document RPO/RTO, test restore and rollback across supported Mosquitto versions, and cover disk-full/corrupt-db behavior.
3. **Add container-level qualification:** MQTT 5 and 3.1.1 CONNECT, anonymous rejection, ACL positive/negative cases, QoS 0/1/2, retained clear/replay, durable sessions, LWT, reconnect, graceful/crash restart, persistence, TLS/mTLS, cert rotation, quotas, malformed config, and least-privilege runtime tests.
4. **Qualify the published multi-arch artifact:** pin Alpine repository/package inputs or build a pinned Mosquitto release, test both target architectures, scan OS and app packages, verify attestations/SBOM, and deploy by digest. Release qualification must not skip the container build/runtime suite.
5. **Harden config generation:** reject directive injection/newlines, constrain hosts/paths/log destinations/prefixes, write owner-only temporary files, run `mosquitto -c <candidate> -t`, and atomically replace last known-good config.
6. **Add operational telemetry:** protected `$SYS` scraping or equivalent, connected/session counts, queue depth/bytes, dropped publishes, retained/store bytes, auth failures, persistence save failures, disk capacity, restarts and latency. Provide a redacted diagnostics bundle and explicit payload/topic/client-ID privacy policy.

### P2 — broaden the supported product slice

1. Add an optional Home Assistant Supervisor-style discovery/secret handoff only if PiPhi intends a managed HA user journey; otherwise clearly document external-broker setup and ownership boundaries.
2. Add WebSocket listeners only with the same TLS, origin, auth, ACL, quota, and health invariants as TCP.
3. Add governed bridge objects with per-bridge principals, verified TLS, topic allowlists/remapping, loop prevention, bounded queues/backoff, status topics/metrics, and secret rotation. Do not expose arbitrary config includes as the primary multi-tenant API.
4. Add retained-message/session administration with dry-run inventory, tenant scoping, expiry policy, safe purge, and audit logging.
5. Publish a tested capacity envelope, failure-mode runbook, backup/restore drill, certificate/credential rotation guide, and explicit known-limitations section.

- External claims use owning Home Assistant and Eclipse Mosquitto sources pinned to commits current at the cutoff where possible.
